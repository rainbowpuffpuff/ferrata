# Security tooling of 11 November 2026: Slither, Aderyn, Halmos, cargo-audit, cargo-deny

The analyses a security reviewer expects, run on the vault (`vault/src`: `FerrataVault`, the linked library
`FerrataRegistry`, the two interfaces) and on every Rust lockfile of the repository, each finding triaged.
Re-run everything with `scripts/security-tools.sh install all` (steps: `install versions slither aderyn halmos audit
deny`); the raw outputs are in [`tools-out/`](tools-out/). This is tooling, not an audit.

**Outcome.** No tool found a real issue in the vault: every Slither and Aderyn result is a false positive or a
design choice the vault documents (below, with the line). Halmos proves the core properties listed in §3 on the
paths it explores (bounds in §3). The Rust advisories are all in third-party crates (RISC Zero, Logos Blockchain,
arkworks, alloy, RustCrypto). None is reachable with attacker input in a Ferrata guest or on the vault's path; the
host-side ones are local timing channels, build-time leaks, parsers of trusted files, or denial of service through
a hostile DNS server in the linked Logos node crates (low). The one on production guests (`ruint`, through
`risc0-binfmt`) is not reachable, and bumping a guest lockfile would change the image ids the vault pins, so it
waits for the next RISC Zero bump. Nothing in `vault/src` changed on this branch, so the vault deployed
on Sepolia (`0xfE3199fa2634413CbAC317371076Cae3EB2d9E54`) needs no redeployment because of this note.

Where it ran: a Modal CPU build box (`mrun`, workspace `ws-5`), branch `sectools` from `integration6`
(`2eb5902`). Measured: every count below is from the outputs in `tools-out/`.

## 3. Halmos: the core properties, checked symbolically

[`vault/test/halmos/VaultHalmos.t.sol`](../../../vault/test/halmos/VaultHalmos.t.sol) (`forge test` does not run
`check_*` functions: with the file present the suite gives 433 passed and 1 skipped of 434, on the build
box, as in `docs/EVIDENCE.md` row 12; the skipped one, the privacy suite's Ethereum half, fails instead when
`target/privacy/` does not exist, as in any fresh worktree). Every argument of a `check_*` function is symbolic; Halmos
explores every path from the state `setUp` builds and proves the assertions on all of them, or prints a
counterexample. That state: the suite's fixture vault (rule (A), RISC Zero's real emergency-stop contract in front
of a verifier that accepts exactly the statements it was given, ETH, USDC, DAI and USDT registered), two ETH
deposits and one USDC deposit, a finalised checkpoint with burn root R1, a finalised and then revoked one with root
R2, and a release of nullifier N0 on R1 to a payee that refuses ETH (so the vault owes it). After `setUp` the
verifier accepts no release statement; a check makes it accept one only where it says so.

### 3.2 How to read the results

A `check_reach_*` FAIL is the expected outcome: Halmos found a counterexample, a concrete path on which the guarded
call succeeds. Without them a PASS could be vacuous; the first run showed why they matter (§3.3: every release
path was lost and the release property passed for the wrong reason).

### 3.3 Two defects of Halmos 0.3.3, fixed locally in the script

1. Its `sha256` precompile declares the uninterpreted function over `arg_size` bits for an `arg_size`-byte input,
   so the first `sha256` the vault computes (the deposit tree) stops it with a Z3 sort mismatch
   (`f_sha256_65 ((_ BitVec 65)) … supplied sort is (_ BitVec 520)`). Fix: `BitVecSorts[arg_size * 8]`.
2. It leaves `sha256` uninterpreted even on concrete input. The vault uses a precomputed domain tag; the test's
   journal computes it with `sha256`; the two never matched, every release path reverted, and the release property
   passed vacuously while `check_reach_release` also passed. The registry's published entries, at
   `sha256`-derived slots, stopped Halmos too (`symbolic storage base slot`). Fix: hash concrete input for real (as
   Halmos does for keccak); symbolic input stays uninterpreted.

Both patches are applied idempotently to the installed copy by `scripts/security-tools.sh halmos`; they are local
(nothing was reported upstream from here). With them, `forge test` and Halmos agree on the concrete case: the release
that `check_reach_release` asserts impossible pays under `forge test` as well
([`replay/HalmosReplay.t.sol`](replay/HalmosReplay.t.sol), `test_release_pays_concretely`, which fails with
"assertion failed" as intended; the file sits outside `vault/test` so the suite's count is unchanged, and its header
says how to run it).

### 3.4 Bounds and model

- One concrete starting state (above), not every reachable state; per property, every path from it.
- Calldata Halmos generates for "any function" checks: dynamic arrays of length 1, byte strings of 4 bytes
  (`--default-array-lengths 1 --default-bytes-lengths 4`); those checks ran under both of Halmos's storage layouts
  (its default "solidity" layout and the "generic" one), see §3.1.
- Loops whose exit depends on a symbolic value are unrolled twice (Halmos's default); the vault's loops in these
  paths have concrete bounds.
- `sha256` of symbolic input is an uninterpreted function: equal inputs give equal outputs, nothing more. A Merkle
  path can therefore "match" for any leaf, which over-approximates `refund` (sound for the properties checked).
- The verifier is modelled as accepting exactly the statements the test registered (RISC Zero's soundness).
- `HALMOS_TIMEOUT` bounds each run (600 s for the targeted checks, 900 s for the entry-point and any-calldata ones,
  `scripts/security-tools.sh halmos-groups`); a run stopped by it has no PASS line and is reported as not finished.

## 5. Real issues

None. No result of any tool is a defect of the vault, so no failing-first test and no fix were written, and nothing
in `vault/src` changed on this branch: the bytecode deployed on Sepolia at
`0xfE3199fa2634413CbAC317371076Cae3EB2d9E54` (the address of the crown runs, `e2e/runs/crown-rehearsal-1/`) is
untouched by it. The analyses are of this tree's vault source; the deployed bytecode itself was not analysed.

**One observation, not a tool finding** (seen while writing `check_after_stop_only_owed_leaves`, whose property
allows the escrow to grow): deposits stay open after the verifier stop. `_checkDeposit` (`FerrataVault.sol:1190-1209`)
does not read `_stopped()`, so until the freeze authority freezes deposits or retires the vault (or anyone retires it
30 days later, since no checkpoint can follow a stop), a new deposit is escrowed and claimable on LEZ, but its escrow
can never be released or refunded, like all escrow after a stop (`vault/README.md`, "Known limits"). Nothing is lost
to a third party and the response is in the freeze authority's hands, so this is informational; refusing deposits
when `_stopped()` would be a design change (D13), not a fix, and is left to the owner.

## 6. Limits

- Tools, not an audit: the detectors find patterns; Halmos proves the stated properties only from the state its
  `setUp` builds, on the paths it explores within the bounds in §3 (loop and array bounds), with the RISC Zero
  verifier modelled as "accepts exactly the statements it was given" and `sha256` as an uninterpreted function (so
  hash equalities hold only between equal inputs and a Merkle path can be "valid" for any leaf: an
  over-approximation, sound for the properties checked).
- cargo-audit and cargo-deny know only published advisories (RustSec database of 11 November 2026).
- The vault is analysed as this tree's source (v5), not as the bytecode deployed on Sepolia.

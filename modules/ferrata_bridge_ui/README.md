# `ferrata_bridge_ui`: the Ferrata mini-app (Logos ui module, prototype)

The Logos mini-app RFP-022 asks for (Usability 02, 05-09): a `ui_qml` module, built with
logos-module-builder like `ferrata_attest_module`, with the user's flows and the admin functions in one UI.
Not audited; a prototype. `RESULTS.md` records what ran.

| Screen | What it does | RFP-022 |
|---|---|---|
| Deposit | fixed denominations from the registry, with fees and total; private destination pre-selected, a public one only after an explicit acknowledgement; account index inside the recovery window; a random claim delay and a permissionless relayer on by default; a live indicator of what the current choices leak; the step's public/private table | U.02, U.05, U.06, U.07 |
| Claim | the wallet's positions with their state; the relayer's root import (a button on the devnet, the relayer daemon's job otherwise); the private claim pre-selected, plaintext only after an acknowledgement; a claim held by the deposit's random delay unless the user overrides it (on the devnet a button lets the delay pass by moving the devnet's clock); the private claim settled with the account's private balance and the proof's kind (real or dev mode); the leak indicator over these choices | U.02, U.05, U.06 |
| Burn and release | burn from a private account by default (public after an acknowledgement), with the private and public holdings shown; a fresh recipient address generated by default; a random delay before the release on by default (the client-proposed delay of `docs/guides/user-guide.md` §9), held unless the user overrides it; the release sent by a relayer that pays the gas | U.02, U.05, U.06 |
| Positions | recovery from the seed alone: every deposit and burn of the wallet, found from the whole deposit list and the zone's history, no per-item query | U.02 (recovery) |
| Registry | per token: registration, denominations, mint, relay, burn and checkpoint fees, escrow, the vault's deposit and release caps and the bridge program's mint and burn caps with their utilisation, freezes | U.02 (registry view) |
| Admin | roles and the cap floor; `SetCap` as the admin; `Freeze` as the freeze authority; what each role can and cannot do | U.02 (admin UI) |
| Privacy | what is public on Ethereum, public on LEZ and private, for deposit, claim, burn and release, and the residual correlations | U.07 |
| Endpoints | the Ethereum RPC address and the LEZ sequencer or zone, applied and tested in place; the backend (devnet or the Logos core module) | U.09 |

Errors are mapped from the program's and the vault's codes to an action (U.08: unsupported token or
amount, cap exceeded, verification failed, not final yet, already claimed or released, frozen,
insufficient balance, endpoint unreachable), and the technical line under the message has hashes and
indices removed, so it does not say which deposit or burn the failed attempt referred to.

## How it is built

```sh
modules/ferrata_bridge_ui/scripts/nix-build.sh [OUT_DIR]   # nix build .#lgx and .#lgx-portable (Linux x86-64, Nix with flakes)
```

- `metadata.json`: `type: ui_qml`, `view: qml/Main.qml`, no C++ backend (the QML view runs in the host's
  process, as logos-module-builder's `ui-qml` template); the builder is pinned to `5f74cdb` with the same
  `flake.lock` as `ferrata_attest_module`.
- `qml/Main.qml` (the view), `qml/js/privacy.js` (the step tables and the leak indicator),
  `qml/js/format.js` (amounts and the error messages).
- `nix run .` opens the module in Basecamp's standalone mode; `nix run .#ui-tests` runs `tests/ui-tests.mjs`
  in Basecamp headless (`scripts/basecamp-ui-tests.sh` pins Basecamp to `b642a9a`). Inside Logos the view
  calls the core module on the user's first action, not at load.

## Where the calls go

Every call is `call(method, params)` with one JSON value in and one out:

- **In Logos** (the host injects `logos`): `logos.callModule("ferrata_bridge_module", method, [json])`, on
  the user's first action. That core module is not built yet (the proposal's §B7 lists it; README
  "Specified but not built"). Basecamp's sandbox refuses a ui module any network access (measured:
  `RESULTS.md`), so inside Logos this is the only path, as the design has it.
- **On the devnet**: HTTP to `cli/examples/miniapp_devnet.rs`, which serves the same methods (`info`,
  `registry`, `price`, `deposit`, `relay`, `scan`, `claim`, `burn`, `checkpoint`, `release`,
  `set_endpoints`, `advance_time` (the devnet's clock, for letting a delay pass), `admin.status`,
  `admin.set_cap`, `admin.freeze`) from a local devnet: the v5 vault on
  anvil (chain id 1, never a public network) with the vault tests' mock verifier, and the zone in the LEZ
  harness (LEZ's state transition with the bridge guest, RISC Zero dev mode). It is the `ferrata` CLI's
  library wired as `cli/tests/e2e.rs` wires it; the relayer's imports and the checkpoint prover are named
  stand-ins in its replies.
- **Private transactions on the devnet** are proven and settled by the harness with the wallet's own keys.
  LEZ's wallet derives private account `/a` from the seed's key tree (`KeyTreePrivate`): an authorization
  secret key `ask` and a viewing secret key `(d, z)`, from which `npk` and the ML-KEM-768 `vpk` follow; the
  account is of kind `Regular`, so its id is `for_regular_private_account(npk, vpk)`. Those three values are
  exactly the harness's `TestPrivateKeys`, so the devnet builds them from the seed (and checks the id against
  the CLI's derivation), and the harness proves each private claim and burn with `lee::execute_and_prove`
  (the privacy-preserving circuit, with `RegularKey::Authorized(ask)` as LEZ's wallet uses it) and settles it
  through LEZ's private settlement, as `lez/harness/tests/bridge_burn.rs` does. The private burn's note
  reaches the zone's history through its public delivery to `token(cid, token)`, where the checkpoint
  program collects it. In dev mode (`RISC0_DEV_MODE=1`) the receipt is a fake one; with
  `FERRATA_DEVNET_PROOFS=real` the devnet proves them for real (r0vm on the CPU, minutes each) and the
  receipt is verified at settlement. Stand-ins of this path, named in the replies: the private account's
  native balance for LEZ fees is put in the state on its first private transaction (as the harness's tests
  fund theirs); the transaction has the harness's bare shape with fresh randomness (LEZ's wallet also pads
  it with dummy inputs, which the harness measures separately as `Shape::Wallet`).

## The wallet SDK

RFP-022 asks for the wallet SDK of the λPrize wallet work. That prize, LP-0021 (LEZ Wallet and Provider
SDK), is open and has no solution yet (logos-co/lambda-prize, `prizes/LP-0021.md`; `solutions/` has none),
so there is no SDK to link. The mini-app follows its flow instead: connect, account selection (the dApp is
named, the user picks the account), and an approval prompt before anything is signed or sent that names
the requesting dApp, the account, the asset, the amount and the destination, and says in words what the
call does (funds moved, approvals granted).

The wallet is reached in two places only, `walletConnect()` and `propose()` in `Main.qml`, and both hand
over to a provider object when one is set as the view's `walletProvider` property:

```js
walletProvider = {
    connect: function (dapp, accounts, done) { /* account selection naming dapp */ done(account /* or "" */); },
    approve: function (request, done) { /* request: { title, rows: [[label, value]], effects: [text] } */ done(true /* or false */); }
};
```

Without one, the built-in prompts play those two calls. When an LP-0021 SDK is released, an adapter of
that shape is the whole switch (the proposal gives four weeks for it); the test injects a stub provider
and checks that the built-in prompts are then not used (`test_14_wallet_provider_seam`).

## Tests

```sh
modules/ferrata_bridge_ui/scripts/box-test.sh            # Linux box with Foundry, RISC Zero (dev mode), Qt 6 qmltestrunner, curl, jq
modules/ferrata_bridge_ui/scripts/basecamp-ui-tests.sh   # Nix: Basecamp (pinned) standalone and headless, tests/ui-tests.mjs
```

`box-test.sh` builds the devnet backend with the `ferrata` tool, so it needs what `cli/` needs (`libpcsclite-dev`,
RISC Zero's guest Rust 1.91.1: [`cli/README.md`](../../cli/README.md)), and Qt 6's test runner with the QML modules the
view imports. On Ubuntu 24.04 (Debian names; checked on the Modal build box, 12 Nov 2026: 17 of 17 passed):

```sh
sudo apt-get install --no-install-recommends qt6-qpa-plugins qml-qt6 qt6-declarative-dev-tools \
  qml6-module-qtquick qml6-module-qtquick-controls qml6-module-qtquick-layouts qml6-module-qtquick-templates \
  qml6-module-qtquick-window qml6-module-qtqml-workerscript qml6-module-qttest qml6-module-qtqml \
  qml6-module-qtqml-models fonts-dejavu-core
```

It rewrites its own files in `results/` (git then shows them changed: timings and screenshots) and keeps the two
logs of `basecamp-ui-tests.sh` there.

The second installs the module in Logos Basecamp and runs Basecamp's own headless UI test: the view loads,
chooses the core-module transport, every screen is built, and the sandbox refuses its network access.

It builds and starts the devnet backend, checks its methods with curl, then drives the view headless
(Qt Quick Test, offscreen) through every screen. **The private round trip on the defaults** (the B3 done
gate): a private deposit with the defaults; the relayer's import; the claim held by its random delay, the
delay let pass on the devnet's clock (not overridden) and a private claim, settled; a private burn of that
holding to a freshly generated address with the release's random delay on, settled; the checkpoint; the
release held by its delay, the delay let pass, and the release by a relayer paying that fresh address. No
default is changed on that path. Around it: wallet connection, endpoints (an unreachable RPC, a refused
sequencer, back), the registry, a public deposit, a plaintext claim and a public burn each only after its
acknowledgement (the public path keeps its warnings), a rejection in the wallet, recovery from the seed,
the error messages, a second release refused, the admin's cap (one refused below the floor), a freeze that
the next claim runs into, and the wallet seam with an injected provider. Each state is saved to
`results/screenshots/`. `FERRATA_DEVNET_PROOFS=real QT_TIMEOUT=3000 scripts/box-test.sh` runs the same test
with the private claim and burn proven for real; its results go to `results-real-proofs/`.

## Not done

- **The private round trip runs on the devnet, not on a LEZ sequencer.** The harness proves and settles
  the private transactions (above); on a sequencer they would be sent by LEZ's wallet. Two things stand
  between the view and that: `ferrata_bridge_module` (the core module the view calls in Logos) is built,
  with the private claim since EVIDENCE row 93, but has not run with the view (`modules/README.md`,
  "Left out"); and the `ferrata` tool's sequencer path has not run against a sequencer: since the merge of
  branch `bridge-cli` its
  ledger (`cli/src/lez.rs`, `Sequencer::applied_with_private`) reads a private burn's note from the delivery
  its transaction makes in the clear (`lez::visible_calls`), and the tool has a private burn (EVIDENCE rows
  84, 85, both in the harness).
- The checkpoint and release proofs and the Groth16 wrap are the mock verifier on the devnet (named in the
  replies); real proofs on this path are the private transactions' only.
- The vault's own admin functions (fee announcements, watchers, the 14-day role change, retirement) are
  shown, not sent; the admin view sends the bridge program's `SetCap` and `Freeze`.
- One token (ETH) on the devnet; ERC-20 deposits need the token's approval step, which the view does not
  have yet.
- Not in a catalog; Linux x86-64 only was tried.

# RFP-021 P.8: in-program BLS12-381 against a hypothetical native precompile, modelled

Generated by `python3 -I bench/perf/precompile_model.py bench/perf/results` from measured inputs (each named below);
the model is the only thing not measured. **A precompile is reachable only from public transactions**: a LEZ
node would run it natively when it executes a public transaction; a private transaction's program runs inside
the zkVM proof, where only RISC Zero's own accelerators exist (the program already uses RISC Zero's accelerated
blst, `v0.3.16-risczero.0`). So the proven path (`VerifyAll` in a private actor) would not gain from it.

**The model.** LEZ charges a public transaction's execution gas as the user cycles the executor meters. A native
precompile would be priced by the work it costs a node; the model prices it at time parity: the native time of
the operation multiplied by the executor's own throughput on the same CPU, so that a node spends the same wall
time per unit of gas inside and outside the zkVM. (A chain would add a safety margin; at ten times the native
cost the conclusions below do not change.) Native times: blst 0.3.16, one thread, the build box's CPU, median
of 300 (`bench/precompile`). Executor throughput: the same step executed five times by RISC Zero's executor
(`perf_prove --exec`), median.

The finality update's three transactions meter **9,228,905** cycles in all (dump-index.tsv); with the
BLS work as a precompile priced at time parity they would meter **902,607**, 10.2x less:
the non-BLS work (884,766: SSZ hashing, Merkle branches, decoding, the job's state) is what remains, and the
whole update would fit one transaction (the target is 5M, the limit 10M) instead of three.

**A handoff** adds the next committee's adoption, two parts of 256 keys: 3,410,995 and 3,418,189 cycles,
each modelled at 4,151 as a precompile (native 269.4 µs per part: deserialize,
check on the curve, recompress and compare, sum). The handoff's five transactions meter
15,997,954; with the precompile about 845,451 (its own Miller step, 3,313,372; the
BLS share of its Open taken as update_1's).

For reference: blst's whole `fast_aggregate_verify` over 512 keys, natively, 1820 µs
(time parity at 13.8 Mcycles/s: about 25,155 cycles); EIP-2537's gas for
the pairing check alone, 102,900, is what Ethereum charges for the operation that costs this program 6.9M cycles.

**What it would change.** On the public path the tracking cost per update (RFP-021 P.3, `perf-tracking.md`) would
fall about 10-fold; the proven path and every private consumer would not change. Whether a
follow-on precompile RFP is warranted turns on how many instances follow Ethereum publicly: at one update every two
hours an instance pays 127,294,275 execution gas a day (measured, `perf-tracking.md`); with the precompile about
12,449,652 (the same days, each update scaled by the ratio above; handoffs alike).

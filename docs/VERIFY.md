# Verify Ferrata from a terminal

A reviewer's path from `git clone` to every check this repository can make of its own evidence, without trusting
the prose: first the offline checks (minutes, Python only), then the online ones (read-only requests to public
endpoints), then the named tests with their toolchains, then a round trip of your own between Sepolia and our public
LEZ test network. Every check prints what it re-checked and against what, and exits non-zero on a failure.

Nothing here is audited. The test network is ours, not a network Logos runs (LEZ testnet 0.4 does not exist).

## 1. Ten minutes: clone, then every offline check

You need git and Python 3.11 or later; Node 20 or later for seven of the checks, OpenSSH's `ssh-keygen` and
`sha256sum` for the Basecamp release check, Foundry (anvil, cast, forge) for four,
and for one of those, the deploy tool's, the vault built first (`cd vault && forge install --no-git
foundry-rs/forge-std@v1.10.0 OpenZeppelin/openzeppelin-contracts@v5.4.0 risc0/risc0-ethereum@v3.1.0 && forge build`):
without them those checks are skipped, and say so. Nothing else is built or installed.

```sh
git clone https://github.com/rainbowpuffpuff/ferrata && cd ferrata
python3 -I scripts/verify.py --list            # every check: its family, mode, requirement rows and EVIDENCE rows
python3 -I scripts/verify.py --all             # the 119 quick offline checks: about 6 minutes
python3 -I scripts/test_verify.py              # the tamper tests: a few minutes (201 s on a laptop)
python3 -I scripts/test_verify_lc.py           # the light-client records' tamper tests: seconds
python3 -I scripts/test_verify_zone.py         # the four-key rc3 run's tamper tests: seconds
python3 -I scripts/test_verify_f13.py          # the F.13 fee records' tamper tests (ADR 0046's and ADR 0048's): seconds
python3 -I scripts/test_verify_f7.py           # the F.7 runs' records' tamper tests: seconds
python3 -I scripts/test_verify_bridge.py       # the bridge records' tamper tests: seconds
python3 -I scripts/test_verify_bridge_rows.py  # the remaining bridge-row records' tamper tests: seconds
```

Each check prints one block, for example:

```text
PASS  run-record  [run-record, offline]  0.1 s
      rows RFP-021 S.1, RFP-022 S.1 · EVIDENCE 242, 248, 271
      re-checked: lez/updater/results/public-network-run/summary.json and RECORD.md: updates applied, committee ...
      against:    the transaction list lez/updater/results/public-network-run/transactions.tsv (one line per ...
      as of LEZ block 25776 (2026-11-26T10:17:22.807Z), as chain.json records it: 2117 transactions to the attestation
      program; the list and chain.json agree (times, hashes, 3 pauses, instances, counters); not read from the chain
      here (run-record-online does)
```

and the run ends with `N checks in T s: N PASS, 0 FAIL, 0 SKIP`. The exit status is 1 if a check failed, 0
otherwise; `--strict` makes a skip a failure too (CI's `verify` job runs `--all --offline --strict`). A check holds a
row's wording to its record: `lc-stage4-attest-costs`, for one, holds RFP-021 P.1's "at most 32.4% of LEZ's 5M target"
to the largest recorded case, 1,619,960 cycles, which is 32.3992% (it failed on the row's earlier "at most 32%" until
the row was corrected); `bridge-import-claim-costs` holds RFP-022 P.2's stated B1 harness range, 231,635–237,169, to
the B1 record's four applied `ImportRoot` cases (it failed on the earlier "237,140", below the vault-B import's
237,169).

What the offline checks re-check, by family (`--list` gives each check):

| Family | Re-checks | Against |
|---|---|---|
| `record` | the numbers the documents state, re-derived from the committed records of the runs (refusal codes and case counts of the light client's security records, the lab's roots, the day-one rehearsal, the M0 checks, the performance figures and state-growth projections regenerated byte for byte, CI's round trip rebuilt against LEZ v0.4.0-rc3, the return leg over four LEZ v0.4.0-rc3 sequencers: its inscriptions, checkpoint, refusals, payments, fork rehearsal and the attestors' resources, the `zone-rc3-multi-*` checks) | the records' own per-case data, and the figures EVIDENCE.md and the status rows state |
| `hash` | the site's manifest, the deployed programs' image ids, the recorded light-client data, the accumulator vectors | git blobs, `docs/image-ids.md`, the fixtures' `SHA256SUMS`, an independent regeneration |
| `seal` | every recorded Groth16 seal (RISC Zero 3.0.0 and 3.1.0), verified in pure Python | its image id and journal; the verifier key of RISC Zero's release |
| `signature` | the Basecamp release's sums, signed with ssh-keygen and minisign | the committed release key and its published fingerprint |
| `run-record` | the light client's unattended run on our test network (section 4) | its transaction list and `chain.json`, against each other |
| `docs` | the row-to-test map, the decision log, the guides, the links, the IDLs, the audit scope's generated inventory | the tracked files and CI's jobs |
| `unit` | the repository's own tools under their tests (Python and Node) | their test cases |

The tamper tests run each family's checks on a copy of the repository with one piece of evidence altered (a byte of a
seal, a transaction hash, a recorded number, a manifest hash, a signature) and require a failure, so a check that
passes whatever its input is caught.

One requirement row, one EVIDENCE row, one family, or the coverage of every row:

```sh
python3 -I scripts/verify.py RFP-021:F.4       # also 021/F.4 or F.4@021; an RFP must be named where both have the row
python3 -I scripts/verify.py evidence:151
python3 -I scripts/verify.py family:seal
python3 -I scripts/verify.py --coverage        # every row of docs/requirements-status.md with its checks
```

## 2. The online checks (read-only)

```sh
python3 -I scripts/verify.py --all --online    # the 22 online checks: about 20 minutes
```

They send only reads (`eth_call`, `eth_getCode`, receipts and logs on Ethereum; `getBlockRange`, `getAccountView` on
LEZ; GETs of the site's files, of beacon-API headers and of GitHub's public API for workflow runs); the clients refuse
anything else. CI's `verify-online.yml` runs them daily. Endpoints: the free public
ones of `scripts/pubnet-endpoints.json`, or yours first with `--sepolia-rpc URL`, `--mainnet-rpc URL`, `--beacon URL`;
our test network's address is in `scripts/reproduce/deployed-programs.json` (`--lez URL` to use another).

| Check | Reads | Shows |
|---|---|---|
| `sepolia-crown-live-1`, `-3`, `-4` | Sepolia | the three live round trips of 11, 12 and 18 November, every transaction against its committed record |
| `sepolia-live-roundtrip` | Sepolia and our test network | the first full round trip on our test network (EVIDENCE row 250), every fact rebuilt from both chains |
| `sepolia-vaults-closed` | Sepolia | the four RISC Zero 3.0 vaults stay closed (every cap zero) |
| `mainnet-risc0-3.0-stopped` | Ethereum mainnet | RISC Zero's Groth16 verifier 3.0.0 is stopped there (its emergency stop paused) |
| `lez-network-programs` | our test network | each deployed program is the one the repository builds (image id, immutable header) |
| `lez-network-head` | our test network and Sepolia beacon APIs | the head block's hash recomputed; each instance's finalized header equal to Sepolia's |
| `run-record-online`, `run-record-counters` | our test network | section 4 |
| `run-record-beacon` | Sepolia beacon APIs | every header the light client applied is Sepolia's canonical block |
| `updater-live-sepolia-beacon` | a Sepolia beacon API | the updater's 8 h live run of 12-13 November, every applied root canonical |
| `site-manifest-online` | the live site | the site serves the files the repository holds |
| `day1-discover-online` | our test network | the day-one kit's read-only probe of the endpoint: health, head, fees, programs, channel, the clock, v0.4 or not |
| `sourcify-status-online` | sourcify.dev | what Sourcify holds for every contract of the crown-live-3 round trip (12 exact matches of EVIDENCE row 122) |
| `sepolia-31-vault`, `sepolia-verifiers` | Sepolia | the RISC Zero 3.1 vault against its deployment record; each vault's verifier 3.1.0, or 3.0.0 only behind closed caps |
| `basecamp-packages-online`, `catalog-index-online` | our test network, GitHub | every Basecamp package served equals its signed sum and carries its two signatures; the module catalog's index names the released packages |
| `gasdrop-terms-online`, `faucet-terms-online` | our test network | the gas drop's published terms and guest; the faucet's published balance equal to the chain's |
| `github-ci-runs` | GitHub's public API | each GitHub Actions run the documents cite concluded as they say (two are recorded failures) |

`run-record-online` reads the network's blocks from block 1 to the record's as-of block (about 40 MB the first
time, a few minutes at the gateway's per-client rate); the blocks it read are kept in `.scratch/verify-cache/` and
read from there on the next run (delete the folder to read them again).

## 3. The named tests (`--tests`)

Every hard requirement row has at least one named test in `scripts/ci/row-tests.toml`; `--tests` runs them, each as
the narrowest command that selects it:

```sh
python3 -I scripts/verify.py RFP-021:F.4 --tests --list    # the commands, without running them
python3 -I scripts/verify.py RFP-021:F.4 --tests
```

They need their toolchains: Rust (`cargo`), Foundry (`forge`), RISC Zero 3.0.5 (`r0vm`, `scripts/ci/install-risc0.sh`),
LEZ's sources beside the repository (`scripts/fetch-upstream.sh`), the consensus vectors (`scripts/fetch-vectors.sh`);
a missing tool is reported as a skip with the command to run once it is there. All of them take hours on one
machine. CI's jobs run most of them (`scripts/ci/check-row-tests.py` shows which job runs which test); 39 run only on a
build machine or by hand (their titles say "not in CI"); 14 are recipes `--tests` lists but never runs, because their
commands have placeholders to fill in or can send transactions (`ferrata-attest … --send`, the day-one kit's `go`):
they print the recipe instead (titles marked "[by hand]").

## 4. The light client's unattended run, from chain data

Since our test network's current chain began on 23 November 2026, a Sepolia instance of the attestation program has
been kept current there by `ferrata-updater`. `lez/updater/results/public-network-run/` reconstructs that run from the
network's public RPC alone: every transaction to the attestation program, decoded (`RECORD.md` gives the figures:
updates applied, committee adoptions and period crossings, every interval between updates, refusals, senders, the
pauses of block production). Its README says what the chain shows and what it does not.

```sh
python3 -I scripts/verify.py run-record             # offline: every figure recomputed from the transaction list
python3 -I scripts/verify.py run-record-online      # the chain: every block read again, every line compared, none missing
python3 -I scripts/verify.py run-record-counters    # each instance's own counter of applied jobs against the chain
python3 -I scripts/verify.py run-record-beacon      # every applied header against Sepolia's beacon chain
```

## 5. A round trip of your own: Sepolia ⇄ our test network, from the command line

What you need: an x86-64 Linux machine with 16 threads and 16 GB for the two private proofs (about 10 minutes each at
16 threads; an hour or more at 8, EVIDENCE row 264), a little Sepolia ETH (0.001 ETH a deposit plus gas), Rust and
LEZ v0.4.0-rc3's sources (`scripts/fetch-upstream.sh`), `r0vm` 3.0.5, and a Sepolia JSON-RPC that serves the vault's
logs from its first block: publicnode's free endpoint answers `pruned history unavailable` for logs older than about a
day; `https://rpc.sepolia.ethpandaops.io` serves them (it rate-limits: the tool stops on its 429s, so run again, or use
your own endpoint). The deployment you use is our test network's (EVIDENCE rows 232, 248): the vault
`0x19499061CeC0BaC2a3E1869Ba5AE6B403aA82787` on Sepolia (deployed in block 12,196,188), the bridge program at account
`36iqVMFpfgHrwoeuVvZhXX3caM1JPBJh56PBw5A4H1rk` (image `0x847a4336…7515`), the network's sequencer behind its gateway at
`<network>/rpc` (`scripts/reproduce/deployed-programs.json`).

**The gateway and LEZ's wallet.** The gateway serves at most 50 blocks per `getBlockRange` and meters each client (HTTP
429 with Retry-After). The tool's own reads of the zone page themselves, but LEZ's wallet, which the tool runs to read
your private holdings and to prove a private claim or burn, syncs in ranges of 100 blocks and stops at the first
refusal: against the gateway directly it stops with `syncing the LEZ wallet with the zone: Request rejected 400`.
Run those commands through a local pager that splits each call into pages of 50 and waits out 429: the private-claim
kit's (`deploy/testnet/cli-rc3/kit_helper.py serve`, which `deploy/testnet/cli-rc3/private-claim.sh` starts; reviewed,
on branch `private-kit`, not yet merged), as the rehearsal below did.

```sh
scripts/fetch-upstream.sh                                   # LEZ's sources beside the repository, at ../upstream/
mkdir -p ../ferrata-src && git archive HEAD | tar -x -C ../ferrata-src
deploy/testnet/cli-rc3/build.sh ../ferrata-src              # `ferrata` against LEZ v0.4.0-rc3: ../ferrata-src/cli/target/release/
export PATH=$PWD/../ferrata-src/cli/target/release:$PATH
export FERRATA_ETH_RPC=<a Sepolia RPC with the vault's logs> FERRATA_CHAIN_ID=11155111
export FERRATA_VAULT=0x19499061CeC0BaC2a3E1869Ba5AE6B403aA82787 FERRATA_FROM_BLOCK=12196188
export FERRATA_SEQUENCER=<network>/rpc                      # or the pager's local URL; <network>: scripts/reproduce/deployed-programs.json
export FERRATA_BRIDGE_ACCOUNT=1f2e94ffdf25a3feca4e0750be66700be3812434c8cf53e0eb301bc493336195   # 36iqVMFp…, in hex
export FERRATA_SEED=$HOME/ferrata.seed FERRATA_LEZ_WALLET=$HOME/ferrata-lez FERRATA_LEZ_PASSWORD_FILE=$HOME/ferrata-lez.pass
```

**Which bridge program the network runs.** Our test network runs `ferrata_bridge_b1` (`0x847a4336…7515`), the bridge
program from before [ADR 0046](decisions/0046-mint-fee-at-deposit.md); this tree builds the program of
[ADR 0048](decisions/0048-protocol-fees-minted-on-lez.md) (`ferrata_bridge_lezfee`, `0x9d02d54d…a321`), whose claims
name no fee schedule (as since ADR 0046) and whose `CollectFees` mints the protocol fees on LEZ, and the network is not
redeployed with it ([`deploy/testnet/F13-REDEPLOY.md`](../deploy/testnet/F13-REDEPLOY.md) is the owner's procedure, not run). The two
programs read their claims differently: B1's `Claim` and `ClaimPrivately` carry a fee-schedule range (24 bytes) that
ADR 0046 dropped, and everything else the tool sends or reads (deposits, burns, releases, every account state) is the
same. `ferrata` built from this tree reads the image id the network's program loader names for `FERRATA_BRIDGE_ACCOUNT`
and builds each claim in that program's layout (`cli/wallet/src/deployed.rs`; EVIDENCE row 281): on this network, B1's,
with the fee-schedule range its token state gives (the claim then shows that range, and `ferrata claim` counts the
anonymity set within it, as B1's claims always did); any other image id is refused before a claim or a burn is built, and
`ferrata status` names the program (`zone: bridge program ferrata_bridge_b1 …`). A private claim or burn is proven with
the binary of the program the network runs: the tool compares `--bridge-program`'s image id with the network's before
proving and refuses another. That binary, `ferrata_bridge_b1.bin` (the image `0x847a4336…7515` under "Superseded" in
`docs/image-ids.md`), comes from `scripts/reproduce/deployed.sh build --out DIR`, which rebuilds every program the
network runs from its recorded source commit (B1 is the guest `ferrata_bridge` of the source `main`, built under
`DIR/work/`; `DIR/main.tsv` gives its image id and sha256); `scripts/reproduce-image-ids.sh build` builds this tree's
programs, `ferrata_bridge_lezfee` among them, which this network would refuse. `ferrata-relayer collect-fees` refuses
this network before building anything (B1 has no `CollectFees`). Check its image id with `r0vm --id` before
using it. What has run of this:
the tests of both layouts (B1's frozen encoding vectors, the loader header of LEZ rc1 and rc3, the claim plans and the
module's session against stand-ins), and CI's round trip on a LEZ v0.4.0-rc3 sequencer of our own with the deployed
B1 binary in place of this tree's program: this tree's `ferrata` sent its plaintext claim in B1's layout, B1 applied it,
and the burn and release followed, 14 of 14 steps (`e2e/runs/rc3-roundtrip-b1/`, EVIDENCE row 281). A send to our test
network with this tree's tool has not been made (this project sends nothing to it).

| Step | Command | What it printed in the rehearsal of 26 November 2026 (a throwaway seed and keystore, no funds, nothing sent) |
|---|---|---|
| keys | `ferrata keys` | the seed's LEZ public and private accounts `/0`-`/2` and the fingerprints of `kAuth` and `kView` |
| status | `ferrata status` | the vault: its deposits and root, `checkpoints 1`, its caps (10 ETH a day each way), the denominations `[0] 0.001 ETH`, `[1] 0.01 ETH`, `[2] 0.1 ETH` with their fees; the zone: `configuration ready`, the instance `active true, 670 jobs applied`, its newest record, the newest imported root, `burns published: 1` |
| deposit | `ferrata deposit --denomination 0 --keystore me.json --password-file me.pass` (a dry run), then again with `--send --yes` | `--denomination` is the index `ferrata status` lists (`0` is 0.001 ETH here). The dry run: `deposit to the vault 0x1949…2787 on chain 11155111`, the denomination 0.001 ETH plus the 0.000002 ETH relay fee (`total 0.001002 ETH`), the destination `your private LEZ account /0 (hidden: C commits to it)` and the commitment C, `claim delay 10 h after the deposit (from your seed)`, the exact call (`would send: to … value 1002000000000000 data 0xf7edb857…`), what becomes public and what stays private, and `not sent: a dry run` (from the unfunded keystore it also said the call would revert, `OutOfFunds`); a deposit needs no archive endpoint |
| wait for the root | `ferrata scan` | `vault 0x1949…2787: 2 deposits at block 12215803, root 0x09b3…71e7 (equal to depositRoot: checked)` and `deposits of this seed: 0`; with a deposit, `not yet imported` until the network's import timer (every 10 minutes; anyone may import) has imported the vault's root, then `claimable under root(n)` |
| claim, privately | `ferrata claim --bridge-program ferrata_bridge_b1.bin`, then with `--send --yes` (through the pager) | with nothing to claim: `nothing to claim: every deposit of this seed is claimed or refunded`; with a deposit, held for its claim delay (1-12 h from the seed; `--no-delay` shortens it and says what that costs), then proven locally, the fee paid from the network relayer's gas drop (no LEZ of your own needed) |
| burn | `ferrata burn --amount 0.001 --recipient 0xFresh --bridge-program ferrata_bridge_b1.bin`, then `--send --yes` (through the pager) | the wallet synced 25,747 blocks in 20 s through the pager, then, with nothing held, `refused: LEZ bridge program exit code 254 INSUFFICIENT_BALANCE (checked before sending: the holding is 0 base units)`; with a holding, proven locally: the burn note public, the holder not |
| checkpoint | `ferrata status` | the network's relayer proves a rule (B) checkpoint once the zone holds a burn and finalizes it after the vault's window (Δ = 3,600 s): the vault's `checkpoints` count rises |
| release | `ferrata release --burn 0` (a dry run), then `--input-out release.input` | with no burn: `no burn with counter 0 of this seed`; with one, the burn root that covers it and the recipient's amount, or before the checkpoint is final `BurnRootNotAccepted` or `ReleaseDelayNotElapsed` with the time it opens |

The transcripts are in `e2e/runs/verify-cli-rc3-dry/`.

The release is the one step that is not yet yours alone on this network. The vault releases against a Groth16 proof of
the release statement; `ferrata release --prove` makes the succinct proof on your machine, but its wrap to Groth16
needs RISC Zero's prover image (Docker, x86-64), and the network's own path today is its operator's: the input handed
to the host, proven on its GPU prover and sent by its relayer (`ferrata-bridge-release`, `deploy/testnet/README.md`),
which also shows the operator which burn is being released. Either way, the release can be checked from Sepolia like
the earlier round trips (`scripts/verify-sepolia.py`, `scripts/verify-live-roundtrip.py`).

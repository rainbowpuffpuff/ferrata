# What the LEZ v0.4 and Logos Blockchain sources say about bridging to Ethereum

## 1. Scope, sources and labels

This note records what the published code says about one question: can an Ethereum contract verify that a token was burned on the Logos Execution Zone (LEZ), and what must it trust? It also collects the surrounding facts a LEZ↔Ethereum bridge depends on.

**Sources, read on 9 November 2026.**
- LEZ, tag [`v0.4.0-rc1`](https://github.com/logos-blockchain/logos-execution-zone/tree/v0.4.0-rc1) (`1806e87`, released 2026-10-29; not marked Latest, v0.3.2 is).
- Logos Blockchain (Bedrock) at [`ee5e344`](https://github.com/logos-blockchain/logos-blockchain/tree/ee5e344) (HEAD on 2026-11-09). LEZ pins an older rev, `d480efc6`.
- [lez-programs@6674d78](https://github.com/logos-blockchain/lez-programs/tree/6674d78), [spel@c6f73ce](https://github.com/logos-co/spel/tree/c6f73ce), [risc0 v3.0.5](https://github.com/risc0/risc0/tree/v3.0.5), [risc0-ethereum v3.0.1](https://github.com/risc0/risc0-ethereum/tree/v3.0.1) and `main`, and the Logos module repositories at the commits linked in §8.

Line links point at the tag or commit above. For other repositories, the link goes to the repository, commit or issue, and the path and lines are given in text.

**Labels.** Unlabelled statements describe what the tagged code does. **Planned** marks something that exists only as a comment, TODO, issue or roadmap entry. **[M]** is a measured or published number. **[E]** is an estimate, with its basis; it has not been measured. **[U]** or UNCONFIRMED means inferred but not tested, or not checked.

## 2. Summary: ten findings

1. A LEZ block has no state root, transactions root, proposer or signature; the only Merkle root in state is the private commitment set's ([`block.rs:51-91`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/common/src/block.rs#L51-L91), [`state/mod.rs:156-175`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lee/state_machine/src/state/mod.rs#L156-L175)).
2. The block hash covers transactions and the `reverted` list, so transaction messages are committed; events and state writes are not ([`block.rs:131-149`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/common/src/block.rs#L131-L149)).
3. `bedrock_status` sits outside the hash and can show `Finalized` early ([#1053](https://github.com/logos-blockchain/logos-execution-zone/issues/1053), open); `Safe` is never assigned.
4. Finality is Bedrock's k-deep LIB as seen by the connected node, with no certificate; about 1 h on the repo's testnet template **[E]**.
5. Validity comes only from re-execution; consensus depends on r0vm cycle counts that a RISC Zero receipt does not contain ([`apply.rs:628-648`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/chain_state/src/apply.rs#L628-L648)).
6. Bedrock has no light client, and leader proofs use UTXO roots that headers do not commit to ([`header/mod.rs:64-72`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/core/src/header/mod.rs#L64-L72)).
7. The only source-proof hook, `l1_inclusion_witness`, "MUST be `None` in v1"; the roadmap's "Native Zone" is post-mainnet ([`cross_zone_inbox/core/src/lib.rs:123-124`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/programs/cross_zone_inbox/core/src/lib.rs#L123-L124)).
8. LEZ's own exits trust sequencer committees; native `Withdraw` is disabled ([`bridge/src/main.rs:24`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/programs/bridge/src/main.rs#L24)).
9. At most 4 privacy-preserving (PP) transactions fit in a block, each paid from the sender's own private account ([`market.rs:44-59`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/programs/fee/core/src/market.rs#L44-L59)).
10. Signed messages carry no chain id ([`public_transaction/message.rs:16`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lee/state_machine/src/public_transaction/message.rs#L16)), and no token program, authority library, SPEL or wallet SDK is released for v0.4 (§8).

## 3. Blocks, finality and state commitments

**Blocks.**
- `Block{header{block_id, prev_block_hash, hash, timestamp}, body{transactions, reverted}, bedrock_status}` ([`block.rs:51-91`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/common/src/block.rs#L51-L91)).
- `hash = SHA256("/LEE/v0.3/Message/Block/" ‖ borsh(id, prev, timestamp, txs, reverted))`; `bedrock_status` is not hashed ([`block.rs:131-149`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/common/src/block.rs#L131-L149)).
- Each block ends with a forced fee transaction, then the clock tick ([`apply.rs:149-168`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/chain_state/src/apply.rs#L149-L168)).
- The timestamp is the producer's wall clock ([`sequencer/core/src/lib.rs:2029`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/sequencer/core/src/lib.rs#L2029)); apply checks only the hash, `id = tip+1` and `prev_block_hash` ([`apply.rs:97-138`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/chain_state/src/apply.rs#L97-L138)).

**Publication.** A block is borsh-encoded as a channel inscription ([`bedrock/src/actor.rs:1041-1045`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/sequencer/actors/bedrock/src/actor.rs#L1041-L1045)) in a Mantle transaction signed with the sequencer's Ed25519 channel key ([`:366-379`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/sequencer/actors/bedrock/src/actor.rs#L366-L379)); that is the only signature on a block. `InscriptionOp{channel_id, inscription, parent: MsgId, signer}` forms a lineage per channel ([`:352-364`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/sequencer/actors/bedrock/src/actor.rs#L352-L364)); `MsgId = Blake2b-256(encode(op))` ([`inscribe.rs:104-109`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/core/src/mantle/ops/channel/inscribe.rs#L104-L109)). Bedrock accepts an inscription only if `parent == tip_message` and `signer == accredited_keys[round_robin(slot)]` ([`inscribe.rs:175-216`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/core/src/mantle/ops/channel/inscribe.rs#L175-L216); [`DECENTRALIZED_SEQUENCING.md:8`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/zone-sdk/DECENTRALIZED_SEQUENCING.md#L8)). Accreditation follows stake ([`sequencer_stake/core/src/lib.rs:196-209`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/programs/sequencer_stake/core/src/lib.rs#L196-L209)).

**Finality.**
- `BedrockStatus` ([`block.rs:79-84`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/common/src/block.rs#L79-L84)): `Pending` at creation; `Finalized` once the inscription is at or below the Bedrock LIB ([`storage/src/actor.rs:247-262`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/sequencer/actors/storage/src/actor.rs#L247-L262)). The indexer streams only up to the connected node's `lib_slot` ([`zone_indexer.rs:44-60`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/chain_state/src/zone_indexer.rs#L44-L60)) and stamps what it accepts `Finalized` ([`block_store.rs:342-343`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/indexer/core/src/block_store.rs#L342-L343)). So `Finalized` means "at least k deep, according to the node LEZ is connected to".
- Followers store an adopted block's inscribed status verbatim, so a block can show `Finalized` early ([#1053](https://github.com/logos-blockchain/logos-execution-zone/issues/1053), open). Treat the field as local metadata.
- `Safe` is set only in a mock ([`mock_service.rs:140-141`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/indexer/service/src/mock_service.rs#L140-L141)).
- Bedrock's LIB is the deepest block within k of the tip; fork choice never switches deeper than k ([`cryptarchia-engine/src/lib.rs:64-86`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/consensus/cryptarchia-engine/src/lib.rs#L64-L86), [`:132-156`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/consensus/cryptarchia-engine/src/lib.rs#L132-L156)); bootstrapping nodes use a density rule ([`:93-128`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/consensus/cryptarchia-engine/src/lib.rs#L93-L128)). There is no finality certificate.
- The repo's testnet template sets k=120, f=1/30, 1 s slots ([`deployment-template.yaml:21-36`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/deployment/ceremony/genesis/testnet/deployment-template.yaml#L21-L36)); live values are UNCONFIRMED. That gives k/f = 3,600 slots, about 1 h plus inclusion **[E]**; LEZ's local docker Bedrock (k=5, f=1/2, [`deployment-settings.yaml:20-30`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/bedrock/deployment-settings.yaml#L20-L30)) about 10 s **[E]**.

**Two tiers and validity.** LEZ keeps a `final` tier from finalized inscriptions and a `head` tier folded over the unfinalized lineage ([`chain.rs:1-3`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/chain_state/src/chain.rs#L1-L3), [`:57-79`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/chain_state/src/chain.rs#L57-L79)). Sequencer and indexer re-execute every block through one `apply_block` ([`apply.rs:88-95`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/chain_state/src/apply.rs#L88-L95)); "any `Err` invalidates the block" ([`apply.rs:338-343`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/chain_state/src/apply.rs#L338-L343)). An invalid finalized block is "Parked": the final tip stays while `final_msg` moves past it ([`chain.rs:476-505`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/chain_state/src/chain.rs#L476-L505)). Invalid finalized inscriptions are slashable faults ([`slasher/src/protocol.rs:24-32`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/sequencer/actors/slasher/src/protocol.rs#L24-L32)).

**State.** `V03State = {public_state, (CommitmentSet, NullifierSet), publications, recovery_bindings}` ([`state/mod.rs:156-175`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lee/state_machine/src/state/mod.rs#L156-L175)). The only Merkle root is the commitment set's ([`:206-209`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lee/state_machine/src/state/mod.rs#L206-L209)), with a `root_history` entry per applied transaction ([`:84`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lee/state_machine/src/state/mod.rs#L84)), served by sequencer RPC `getProofsAndRoot` ([`rpc/src/lib.rs:119-133`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/sequencer/service/rpc/src/lib.rs#L119-L133)) and visible on chain only inside private transactions. Nullifiers, publications and bindings are plain sets and maps ([`state/mod.rs:111-129`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lee/state_machine/src/state/mod.rs#L111-L129)). No state commitment appears in blocks or inscriptions.

## 4. What an outside verifier would have to establish

A contract releasing funds against a LEZ burn needs three facts: inclusion (O3), validity of the block and its ancestors (O2), and finality of the inscription on Bedrock (O1).

### O3: the burn is in a given LEZ block

**Exists.** The block hash commits to the transactions and `reverted` (§3), so a RISC Zero guest can recompute hashes, check `prev_block_hash` continuity, find a burn and check it is not reverted. A burn is committed if it appears in the transaction's public message: a public root call, or a private transaction's boundary message to the bridge program. It is **not** committed as an event (events are computed during apply, [`apply.rs:145-262`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/chain_state/src/apply.rs#L145-L262)) or as a state write (no state root).

**Limits.** A burn reached only through a nested call does not appear in the message. The burning program must be immutable, or its owner can redefine a burn (`immutable` flag, [`state/mod.rs:335-339`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lee/state_machine/src/state/mod.rs#L335-L339)). O3 alone says nothing about validity or finality: anyone can compute a LEZ block hash.

**Cost [E].** One hour of blocks (about 0.4 MB empty, plus about 223 KB per private transaction) is roughly 5–20M guest cycles including signature checks, about 6–25 min of CPU at the measured M2 Pro rate, plus recursion and an x86 Groth16 wrap.

### O2: the block and its ancestors are valid

**Exists.** No proof of any kind. The only hook, `l1_inclusion_witness`, is "Reserved for a future source-state proof; MUST be `None` in v1" ([`cross_zone_inbox/core/src/lib.rs:123-124`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/programs/cross_zone_inbox/core/src/lib.rs#L123-L124)) and asserted `None` ([`cross_zone_inbox/src/main.rs:40-43`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/programs/cross_zone_inbox/src/main.rs#L40-L43)). Earlier explorations were closed: [#512](https://github.com/logos-blockchain/logos-execution-zone/issues/512), [#645](https://github.com/logos-blockchain/logos-execution-zone/issues/645), [#68](https://github.com/logos-blockchain/logos-execution-zone/issues/68) (frozen, private-state provability), [#57](https://github.com/logos-blockchain/logos-execution-zone/issues/57) (pre-rewrite; no code survives).

**Blocks a proof today.**
- *Metering.* Cycle counts from the host-side executor ([`program/mod.rs:104-162`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lee/state_machine/src/program/mod.rs#L104-L162)) decide fees ([`apply.rs:628-648`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/chain_state/src/apply.rs#L628-L648)), refunds ([`:666-698`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/chain_state/src/apply.rs#L666-L698)), the 10M block gas cap ([`market.rs:10-15`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/programs/fee/core/src/market.rs#L10-L15)) and out-of-gas reverts ([`program/mod.rs:139-154`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lee/state_machine/src/program/mod.rs#L139-L154)). The forced fee transaction is byte-compared against the recomputed summary ([`apply.rs:221-234`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/chain_state/src/apply.rs#L221-L234)). A RISC Zero `ReceiptClaim` is `{pre, post, exit_code, input, output}`, with no cycle count (risc0 v3.0.5, `risc0/zkvm/src/claim/receipt.rs:57-72`), and out-of-gas is an executor error, not a provable exit. A guest must replicate r0vm's user-cycle accounting exactly, or LEZ must change its rule; any mismatch accepts blocks nodes reject, or the reverse.
- *No state root.* A guest would keep its own commitments over accounts, the commitment-tree frontier, root history and nullifiers. This needs no header change.
- *Composition.* The native token and loader run as in-host Rust ([`public_backend.rs:58-93`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lee/state_machine/src/validated_state_diff/public_backend.rs#L58-L93)); `env::verify` resolves only `Halted(0)` claims ([`program/mod.rs:189-191`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lee/state_machine/src/program/mod.rs#L189-L191)). Private receipts compose, but nodes also check root history and nullifier freshness ([`state/mod.rs:606-626`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lee/state_machine/src/state/mod.rs#L606-L626)) and `Disclosed` claims against live state ([`validated_state_diff/mod.rs:618-651`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lee/state_machine/src/validated_state_diff/mod.rs#L618-L651)), outside the receipt.
- *No sound slice.* One failing transaction voids the block; nonces advance on any signed transaction ([`state/mod.rs:396-400`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lee/state_machine/src/state/mod.rs#L396-L400)); fees move native balances ([`apply.rs:597-689`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/chain_state/src/apply.rs#L597-L689)).
- *Inherited gap.* A deposit or dispatch "forged in the injection shape still passes" ([`apply.rs:378-379`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/chain_state/src/apply.rs#L378-L379), [#809](https://github.com/logos-blockchain/logos-execution-zone/issues/809)); this does not affect a token only one program can mint.
- *Churn.* Loader panics become chargeable errors via `catch_unwind` ([`validated_state_diff/mod.rs:507-520`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lee/state_machine/src/validated_state_diff/mod.rs#L507-L520)); the final-tier rule has an open TODO ([`chain.rs:369-391`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/chain_state/src/chain.rs#L369-L391)); see also [#935](https://github.com/logos-blockchain/logos-execution-zone/issues/935), [#1023](https://github.com/logos-blockchain/logos-execution-zone/issues/1023), [#1040](https://github.com/logos-blockchain/logos-execution-zone/issues/1040).

**Cost [E].** About 10k non-test lines on the apply path; 4–9 engineer-months for a guest replica, provided metering is settled **[E]**. An empty block holds about 5 fee and clock calls, each proving in 4.4–9.0 s on CPU **[M]** ([`cycle_bench.md:66-81`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/docs/benchmarks/cycle_bench.md#L66-L81)), so about 2–5 min per block on an M2 Pro **[E]**, against a 10 s interval (docker config [`sequencer_config.json:5`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/configs/docker-all-in-one/sequencer_config.json#L5); testnet [U]).

### O1: the inscription is final on Bedrock

**Exists.** Since Bedrock requires `parent == channel.tip_message` ([`inscribe.rs:186-193`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/core/src/mantle/ops/channel/inscribe.rs#L186-L193)), O1 reduces to "the channel's tip message at LIB is M". Inclusion in a Bedrock block is a Blake2b Merkle path to `body_root` ([`transactions/mod.rs:28`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/core/src/mantle/transactions/mod.rs#L28); [`utils/merkle.rs:14-31`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/core/src/utils/merkle.rs#L14-L31); [`block/mod.rs:523-534`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/core/src/block/mod.rs#L523-L534)), meaningful only in a valid, final block.

**A light client would verify** header linkage (`slot, parent_block, body_root, proof_of_leadership`, [`header/mod.rs:64-72`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/core/src/header/mod.rs#L64-L72)); the Ed25519 header signature ([`block/mod.rs:513-521`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/core/src/block/mod.rs#L513-L521)); the leader proof, Groth16 over BN254 verified with arkworks ([`pol/src/lib.rs:76-130`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/zk/proofs/pol/src/lib.rs#L76-L130)), with 9 public inputs including `aged_root` and `latest_root` ([`pol/src/inputs.rs:85-142`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/zk/proofs/pol/src/inputs.rs#L85-L142)); and the k-deep rule from a trusted checkpoint.

**Blocks it.**
- Nodes take `aged_root` (epoch snapshot) and `latest_root` (live UTXO tree) from ledger state ([`cryptarchia/mod.rs:511-534`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/ledger/src/cryptarchia/mod.rs#L511-L534)). Headers commit to neither, so a verifier must replay the Mantle ledger, including a Groth16 `ZkSign` check per transaction ([`zksign/src/lib.rs:11-21`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/zk/proofs/zksign/src/lib.rs#L11-L21)).
- Total stake is inferred from block density ([`cryptarchia/mod.rs:295-303`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/ledger/src/cryptarchia/mod.rs#L295-L303)), so honest majority is assumed. Long-range forks need a weak-subjectivity checkpoint, and a contract cannot run the density comparison on chains it never sees.
- No light-client code or specification exists in either repository; the nearest item is "Checkpoint for Chain Bootstrapping", [logos-blockchain#1454](https://github.com/logos-blockchain/logos-blockchain/issues/1454) (open since 2025-07-16).

**Cost [E].** RISC Zero accelerates `substrate-bn`, `k256`, `curve25519-dalek`, `sha2` and BLS12-381, but not Blake2, Poseidon or `ark-bn254` ([precompiles](https://dev.risczero.com/api/zkvm/precompiles)). Per header: PoL Groth16 ~10–30M cycles accelerated (probably 10× more on arkworks [U]); Ed25519 0.2–1M; ledger replay ~30–100M at the template's 2 tx/block ([`deployment-template.yaml:49`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/deployment/ceremony/genesis/testnet/deployment-template.yaml#L49)). With k+1 = 121 headers per window that is 3.6–12B cycles per finality proof and 86–288B per day. At 73 µs per padded cycle on an M2 Pro CPU **[M]** ([`cycle_bench.md:62-86`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/docs/benchmarks/cycle_bench.md#L62-L86)), keeping up takes 70–240 CPU-days per day **[E]**.

**Bottom line.** O3 is feasible now. O1 and O2 are not provable on v0.4: each needs a multi-month component (a zk Bedrock full node; an exact metering replica) plus continuous proving of both chains **[E]**.

## 5. How LEZ's own bridges handle the same question

**Native `bridge`.** `Deposit{l1_deposit_op_id, recipient_id, amount}` is top-level only, replay-guarded by a receipt PDA, pays from custody, public recipients only ([`bridge/src/main.rs:12-56`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/programs/bridge/src/main.rs#L12-L56)). The sequencer builds it from an observed Bedrock deposit and "pins" it with a channel transfer so it "is valid only on a branch holding all of them" ([`bedrock/src/actor.rs:390-417`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/sequencer/actors/bedrock/src/actor.rs#L390-L417)); the pin needs `transfer_threshold` = `max(1, min(⌈2n/3⌉, n−1))` committee signatures ([`committee_discovery.rs:25-35`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/sequencer/core/src/committee_discovery.rs#L25-L35)). Apply does not check deposits against L1 ([#809](https://github.com/logos-blockchain/logos-execution-zone/issues/809); [#1032](https://github.com/logos-blockchain/logos-execution-zone/issues/1032), "Followers accept forged-shape bridge Deposits with no L1 check", open, high). `Withdraw` panics: "Withdraws are disabled in the current version of LEZ" ([`bridge/src/main.rs:24`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/programs/bridge/src/main.rs#L24)).

**Withdrawals.** Bedrock-side channel withdrawals need `transfer_threshold` committee signatures ([`BRIDGING.md:13`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/zone-sdk/BRIDGING.md#L13)). The roadmap says "withdrawals from the channel are authorized by a quorum of the zone's sequencers"; the fix, "Sequencer Collusion Resistance" (v0.5), is "TBD" (planned; `sequencer_collusion_resistance.md` in [logos-co/roadmap](https://github.com/logos-co/roadmap)).

**Cross-zone messaging.** On zone B, `bridge_lock::Lock` escrows and emits to an outbox ([`bridge_lock/src/main.rs:16-100`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/programs/bridge_lock/src/main.rs#L16-L100)). ## 6. Privacy-preserving transactions

## 7. Time, events, identity, immutability

**Time.** The last transaction of each block ticks clock accounts every 1, 10 and 50 blocks, so during block N `CLOCK_01` holds N−1 ([`clock/core/src/lib.rs:6-46`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/programs/clock/core/src/lib.rs#L6-L46)). **Events.** `Response::event(ProgramEvent{selector, data})`, selector = first 8 bytes of `sha256("<program>::<Event>")` ([`core/src/program/mod.rs:701-720`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lee/state_machine/core/src/program/mod.rs#L701-L720)), stamped with the emitter ([`validated_state_diff/mod.rs:560-566`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lee/state_machine/src/validated_state_diff/mod.rs#L560-L566)), queried off-chain via `getEvents` / `subscribeToEvents` ([`indexer/service/rpc/src/lib.rs:47-48`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/indexer/service/rpc/src/lib.rs#L47-L48)). They come from LEZ's own work merged 2026-08-27; the sources differ on scope ([PR #705](https://github.com/logos-blockchain/logos-execution-zone/pull/705) alone, or "PRs #705–#802"). **Identity.**

- Public signatures are BIP-340 Schnorr on secp256k1 ([`signature/mod.rs:46-80`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lee/state_machine/src/signature/mod.rs#L46-L80)).

## 9. RISC Zero on Ethereum

- **Verifier** ([risc0-ethereum v3.0.1](https://github.com/risc0/risc0-ethereum/tree/v3.0.1)): `verify(seal, imageId, journalDigest)` checks a 4-byte selector and a Groth16 proof with 5 public inputs (`contracts/src/groth16/RiscZeroGroth16Verifier.sol:145-183`). Base verifiers are stateless and immutable. `RiscZeroVerifierEmergencyStop` can be stopped by its guardian; `RiscZeroVerifierRouter`'s admin adds and removes verifiers.
- **Version.** Groth16 verifier 3.0.0, selector `0x73c457ba`, at `0x2a098988600d87650Fb061FfAff08B97149Fa84D` on mainnet, Sepolia, Hoodi and Arbitrum (`contracts/deployment.toml` on [`main`](https://github.com/risc0/risc0-ethereum)). Its control root and BN254 control id match [risc0 v3.0.5](https://github.com/risc0/risc0/tree/v3.0.5) (`risc0/circuit/recursion/src/control_id.rs:53-59`). That a 3.0.5 receipt carries this selector is [U].
- **What to pin.** The base verifier, or a deployer-owned emergency-stop proxy (stop only, no swap). The router lets RISC Zero's admin add verifiers (timelock 259,200 s on mainnet, **1 s** on Sepolia and Hoodi); RISC Zero's own emergency-stop proxy lets its guardian halt releases.
- **Gas [E]:** about 0.22–0.26M per verification (211,750 gas of EIP-1108 precompiles); unmeasured. `RiscZeroSetVerifier` amortizes to about 5–15k per later claim **[E]**.
- **Platform.** "The Groth16 prover currently only works on x86 architecture… Apple Silicon is currently unsupported (even via Docker)" ([local proving](https://dev.risczero.com/api/generating-proofs/local-proving)). LEZ pins `risc0-zkvm 3.0.5`, Rust 1.98.1 ([`Cargo.toml:149-152`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/Cargo.toml#L149-L152)); reproducible builds use `r0.1.91.1` ([`Justfile:16-40`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/Justfile#L16-L40)). LEZ's `sha2` 0.10.9 is newer than RISC Zero's patch list (0.10.8).

## 10. What would make a trustless outbound leg possible

**Without protocol changes,** the most the code permits is: a RISC Zero guest proves O3 (hash-chain continuity from the last accepted tip, extraction of non-reverted burns aimed at a pinned immutable program), and O1/O2 come from a t-of-n signature by the channel's accredited sequencers over the final tip. Safety then holds unless t of n sequencers sign a tip outside LEZ's canonical final tier: the same committee trust LEZ's withdrawals use ([`BRIDGING.md:13`](https://github.com/logos-blockchain/logos-blockchain/blob/ee5e344/zone-sdk/BRIDGING.md#L13)). It does not remove trust in validators, and v0.4 cannot slash a false attestation, since `Slash` carries no proof ([`sequencer_stake/core/src/lib.rs:312-321`](https://github.com/logos-blockchain/logos-execution-zone/blob/v0.4.0-rc1/lez/programs/sequencer_stake/core/src/lib.rs#L312-L321)).

**Protocol changes that would remove that trust:**
1. **Provable metering**: fees and limits that do not depend on unattested r0vm cycle counts, or a specified cycle accounting a proof may emulate.
2. **A state commitment in the block hash** (state root, nullifier commitment or receipts root). [#1023](https://github.com/logos-blockchain/logos-execution-zone/issues/1023) proposes receipts replacing `reverted`, without a root.
3. **A Bedrock light client**: headers committing to ledger state, and a specification beyond [#1454](https://github.com/logos-blockchain/logos-blockchain/issues/1454).
4. **A defined `l1_inclusion_witness`** and zone validity proofs. The roadmap's "Native Zone" ("ZK proven zones where the state transition function (STF) is enforced by the base-layer") is post-mainnet, spec and implementation unchecked (planned; `native_zone.md` in [logos-co/roadmap](https://github.com/logos-co/roadmap)).
5. **Smaller fixes**: drop `bedrock_status` from inscriptions; define or remove `Safe`; domain-separate transaction hashes; proof-carrying slashing.

**Open questions for Logos.**
1. Is a LEZ state or receipts root planned, and would #1023 put receipts under a root in the block hash?
2. What will `l1_inclusion_witness` contain? Is a zone validity or settlement proof planned?
3. Is there a Bedrock light-client specification beyond #1454? Will headers commit to ledger state?
4. Is provable metering planned, or would emulating r0vm's cycle accounting be accepted?
5. Is a t-of-n attestation by accredited sequencers acceptable as "the security of the LEZ network" on testnet 0.4, and with what n and t?
6. What are the live testnet-0.4 values of k, f, slot length, block interval and committee size?
7. Will `bedrock_status` leave inscriptions, and what is `Safe` for?
8. When will a token program, a freeze library and SPEL support v0.4, and when do `lez_core` #72/#74 land?
9. Which module will carry verified light-client APIs, and will `eth_getProof` be available through the verified path?

## 11. Observed since: real blocks, and v0.4.0-rc2

Added 11 November 2026. Unlike §§1–10, these come from running the code, not from reading it.

**On real blocks.** The lab's chain (`lez/lab/`: LEZ v0.4.0-rc1's sequencer with one Logos Blockchain
node at `d480efc6`, one validator, leader proofs in dev mode; one sequencer, not a network) was read back
from its record and from a copy of the node's state, 202 LEZ blocks and their 202 inscriptions
([`checkpoint/RESULTS.md`](../../checkpoint/RESULTS.md), "Real LEZ blocks"; outputs in
`checkpoint/realblocks/out/`, record in `lez/lab/results/record/`):

- **Blocks are inscribed `Pending` and served `Finalized` [M].** All 202 blocks carry
  `bedrock_status = Pending` (0) in the bytes inscribed on Bedrock, and the sequencer's RPC serves them
  with `Finalized` (2). The block hash leaves the byte out (finding 3), so hashes agree; but an
  inscription signs the inscribed bytes, so a prover that checks the inscription's signature must take
  the block's bytes from the inscription, not from the RPC.
- **The channel's posting timeframe is 0 on Bedrock, against LEZ's configured 300 [M].** The node
  reports channel `0x01…01` with `posting_timeframe` 0, `posting_timeout` 0 and `config_tip_hash` 0:
  `sequencer_service setup --create-channel` created it without a configuration op, although the
  sequencer's configuration says 300. Under SPEC-v3 D3 (a rotation's timeframe must equal the bound one
  and must not be 0) no key rotation of such a channel could be accepted, and a rule (A) vault needs a
  non-zero turn: a bridge's channel must be created with a configuration op.
- **Every inscription is `[ChannelInscribe, Transfer]` of the sequencer's own block [M]**, as read from
  the code (§4, O1); observed on this one-sequencer devnet only.

**v0.4.0-rc2** (`e3edf474`, tagged 9 November 2026, 59 commits after rc1;
[`lez-rc2-changes.md`](lez-rc2-changes.md), measured in [`lez/RESULTS.md`](../../lez/RESULTS.md) §10,
`lez/results/v0.4.0-rc2/`, `lez/live/results/v0.4.0-rc2/`):

- Program loader (#943): loader state is a tagged `LoaderEntry` (`ProgramHeader::from_bytes` became
  `from_loader_actor_state`); `WriteSegment` needs an authorised target; the loader is charged one cycle
  per byte of loader state it reads, so deployment, free of execution gas on rc1, now pays it [M]: 373,910
  for LEZ's `scripted` (4 transactions), 1,022,658 for the program (7 transactions); genesis checks a
  builtin's image id.
- The privacy circuit refuses two program-image witnesses for one account, and its image changed: no rc1
  receipt verifies on rc2.
- Wallet (#1035 and others): every public send is simulated; the declared gas limit becomes the
  measurement plus 25 % unless pinned; a send whose simulation reverts is refused unless
  `set_allow_revert(true)`; `DryRun` carries a report; `private_fee_headroom_blocks` was renamed.
- Bedrock test chain (#1063): 4 s slots (was 1 s) and depth 3 (was 5), epochs of 240 s; blocks were final
  14–25 s after publication on the rc2 sequencer, 5–6 s on rc1 [M].
- Unchanged: `lee_core`'s program-facing API, `chain_state`'s block application, the RPC, risc0 3.0.5,
  the Bedrock pin `d480efc6`. Ferrata's guests built against rc2 unchanged, and every harness table row
  (438) equals rc1's [M]; no real proof has been made on rc2.

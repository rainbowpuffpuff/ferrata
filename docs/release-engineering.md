# Release engineering: one command for every number, every M0 check and every release

**Milestones M0, A4 and B4. Written 11 November 2026.** The proposal promises that `just bench` regenerates its
performance numbers with real proving and records the hardware (§B8), that `just m0` prints every M0 check with
its value (M0), and, for A4 and B4, releases ready for testnet 0.4 and a deployment that is one command on the day
it opens. This note says what each command does, what it was run on and what it gave. Paths are relative to the
repository root. Labels as elsewhere: **measured** (a run, with where it ran), **derived**, **estimated**,
**not built**. The code is a prototype, not audited and not for production.

| Command | Script | What it does | Where it runs |
|---|---|---|---|
| `just bench` | `scripts/bench.sh box`, `scripts/bench_report.py` | hardware record, the vault's gas, the light-client cycles, a real proof of the release program; `bench/report/<UTC time>-<commit>/REPORT.md` | the build machine (`FERRATA_BOX`) |
| `just bench-user` | `scripts/bench.sh user-stage`, `user-prove` | the user-side proofs (private attestation, claim, burn, padded as LEZ's wallet pads) proven for real in containers held to `BENCH_CPUS` CPUs (default 16, the declared minimum) and 16 GiB | build machine, then Modal (`BENCH_MODAL_PROFILE`) |
| `just m0` | `scripts/m0.py` | the four M0 checks with their measured values and GO / NO-GO / OPEN; `--online` re-reads the upstream tags; `--json FILE`; `--strict` | anywhere (Python standard library) |
| `just release VERSION` | `scripts/release.sh`, `scripts/release_manifest.py` | builds the six guests (path-independent ids), the vault and the CLI; packages them with `MANIFEST.json` and `SHA256SUMS`; verifies; records the manifest in `releases/VERSION/` | the build machine |
| `just release-verify DIR` | `scripts/release.sh verify` | every checksum, the manifest, the third-party notices, the six programs' image ids recomputed with `r0vm` (said so when `r0vm` is absent; `--strict` fails then) | anywhere |
| `just deploy-testnet ...` | `scripts/deploy-testnet.sh` | deploys a release on a LEZ testnet and an EVM chain; plan only unless `--send` | the deployer's machine |
| `just halmos-long` | `scripts/halmos-long.sh` | the four Halmos properties that did not finish in 900 s, with a longer budget | the build machine |

`FERRATA_BOX` is a command prefix that runs a shell command on a build machine; empty, the stages run where `just`
runs. For this project's Modal build box: `FERRATA_BOX="../modal-build/mrun --profile <workspace> --"` and, to bring
a built bundle back, `FERRATA_BOX_FETCH="../modal-build/mrun --profile <workspace> --no-sync --get"`. Every recipe is
a thin wrapper of a script that runs without `just` too.

## 3. Releases

`just release VERSION` (`scripts/release.sh build`, `package`, `verify`, `record`) makes one bundle,
`ferrata-VERSION/` and `ferrata-VERSION-x86_64-linux.tar.gz` with its `.sha256`:

| Part | Files | What the manifest says of each |
|---|---|---|
| `programs/` | `ferrata_lez.bin` (attestation program) and `ferrata_bridge.bin` (bridge program): LEZ program ELFs, deployed with LEZ's program loader; `checkpoint.bin`, `checkpoint_b.bin`, `segment.bin`, `release.bin`: R0BF binaries (`ferrata-e2e program-binary`); `ids.txt`, `ids.jsonl` as the build wrote them | bytes, sha256, image id, role (which vault immutable it is) |
| `vault/` | `FerrataVault.json`, `FerrataRegistry.json` (forge artifacts: ABI, creation and runtime bytecode, the vault's with solc's link placeholder for the library); `script/DeployVault.s.sol`, `script/deploy.sh`, `script/params/*.json` | compiler, EVM version, optimizer, creation and runtime sizes, sha256 of each bytecode, link references; EIP-170 checked |
| `cli/` | `ferrata` (x86_64-unknown-linux-gnu, built `--locked`: the binary `check-build` passed), `check-build.json` (that record: the binary's sha256, the archives verified after the build), the `Cargo.lock` it was built with, `crates.tsv` (the crates linked into it and the standard library's) | bytes, sha256; `native`: the two prebuilt native archives it links, with their components and licences, from the record; `build`: BUILD-OK's commit and hashes |
| licences | `LICENSE-MIT`, `LICENSE-APACHE`, `THIRD-PARTY-NOTICES.md`, `licenses/` (from [`releases/third-party/`](../releases/third-party/THIRD-PARTY-NOTICES.md)); `THIRD-PARTY-CRATES.md` and `licenses/rust-std-COPYRIGHT-library.html`, generated by the build ([`scripts/crate_notices.py`](../scripts/crate_notices.py)) | bytes, sha256; `licence`: the source's (MIT OR Apache-2.0) and the binary's as a combined work |
| top | `deploy-testnet.sh`, `toolchains.txt` (rustc, r0vm, forge, solc, LEZ commit checked, the native archives' sha256s, build host), `MANIFEST.json`, `SHA256SUMS` | version, commit, creation time, targets, status ("prototype, unaudited: for testnets only") |
| beside it | `ferrata-VERSION-third-party-sources.tar` (+ `.sha256`): the GMP sources of the source offer | `third_party.sources`: bytes, sha256, every member's bytes and sha256 (checked against the pins) |

**Only a build whose every step passed is released (review-fix-supply M-2).** `release.sh build` removes an earlier
build's `BUILD-OK`, CLI and notices first. The CLI step builds, runs `check-build --binary ferrata` (which fails
unless cargo reported success and built the executable inside `cli/target`; an inherited `CARGO_TARGET_DIR` is
dropped), copies the binary it checked with its record (`check-build.json`), and generates the crate notices, into
`build/cli.partial`, renamed `build/cli` only when all of that passed; the native lines of `toolchains.txt` come from
the record. `build/BUILD-OK` (the commit, and the sha256 of the binary, the record and the notices) is written only
when the guests, the vault and the CLI all passed. `package` refuses a build without it, or whose binary, record or
notices are not the ones it names; `release_manifest.py make` takes the `native` section from the record, and
`check` refuses a release whose CLI is not the binary its record and `BUILD-OK` name.

**The crates' notices (review-fix-supply M-1).** The build also writes `THIRD-PARTY-CRATES.md` from its own
dependency graph: `cargo tree -e normal,no-proc-macro --target x86_64-unknown-linux-gnu -p ferrata-cli` (the
packages linked into the binary, with the build's feature resolution), each checked against the build's own
compiler messages; for every third-party crate, its licence (one alternative where it offers a choice: Apache-2.0
where offered, else MIT) and the licence, copying and notice files of its package; for the crates that compile
native code from their own sources (AWS-LC, ring, RocksDB, NVTX), every such file in the package and the SPDX
identifiers and copyright lines of their C, C++ and assembly sources; and the standard library's crates (the
toolchain's rlibs: std's own copies of object, addr2line, miniz_oxide and adler2 are not in the toolchain's
`COPYRIGHT-library.html`, which the release ships too). `release.sh verify` checks that the notices name the
release's lockfile and dependency set, list every crate of it, and that every crate whose symbols are in the binary
(`nm`, Rust v0 demangling) is listed.

**The native code in the CLI (review-code-ops M1, M2).** The CLI links code that cargo does not build from source:
LEZ's wallet pulls in the Logos Blockchain node's proof crates, whose build scripts download two prebuilt archives
with no checksum, rapidsnark (with GMP 6.3.0 and ffiasm) and the Logos circuits (circom-generated witness generators
with circom's C++ runtime, circomlib, GMP 6.2.1, and the circuits' proving keys, which the binary embeds).
[`scripts/native-deps.json`](../scripts/native-deps.json) pins each archive by size and sha256 (each confirmed two
ways: GitHub's own digest, and two downloads on different days or the circuits repository's own Nix pin) and the
sha256 of every library and key file inside. `release.sh build` first runs
[`scripts/fetch_native.py`](../scripts/fetch_native.py) `env`, which downloads each archive once, checks it before
unpacking and again on every later use (a corrupted or replaced cached archive stops the build; it is never used or
silently replaced), and points the build scripts at the result (`RAPIDSNARK_LIB_DIR`, `LBC_ROOT_DIR`); it then checks
that `../upstream/lez-v0.4.0-rc1` is at `1806e873` (it no longer writes the expected commit when it cannot read the
real one), builds the CLI with `--locked`, and runs `fetch_native.py check-build` on cargo's build-script messages,
which fails if `rust-rapidsnark` or a circuits sys crate linked from anywhere but the checked archive, or if any build
script linked native code from outside the build and the system library directories. The binary statically links
GPL-3.0 code (circom's runtime) and LGPL-3.0 code (GMP, rapidsnark, ffiasm, circomlib), so as a combined work it is
conveyed under the GPL version 3 (the cautious reading; the repository's source stays MIT OR Apache-2.0):
`THIRD-PARTY-NOTICES.md` says so, lists every archive with its sha256 and every component with its version, licence
and source, carries the notices and texts, explains relinking (LGPL-3.0 section 4) and makes the source offer.
`release_manifest.py make` and `check` refuse a release whose notices miss an archive, a component or a licence text,
and `deny.toml` declares the native licences against the five crates that link them, so `cargo deny` sees them.
Release 0.1.0-rc.1 predates all of this: its manifest has no `native` or `build` section and it carries no crate
notices, so `verify` fails on it by design, and `deploy-testnet.sh` refuses it.

**Run on the build box, 22 November 2026** (branch `fix-supply` at `68298533`, **measured**; a test release
`0.0.0-fix-supply`, not recorded): `release.sh build` 10 min 42 s (guests, vault and the CLI, `--locked`, from the two
checked archives; `check-build` passed), `package`, `verify --strict`: 18 files, 0 bad, the notices cover the 2
archives and their 8 components, the six programs' image ids recomputed with `r0vm` equal the manifest's, and all six
equal the crown run's table (`e2e/crown/README.md`). The CLI binary: 30,375,968 bytes; it needs only
`libpcsclite.so.1` and the C/C++ runtime at run time (no `librapidsnark.so`), holds 198 GMP symbols and 239
`Circom_CalcWit` strings, and no path of either archive. The tarball 11,475,810 bytes; the sources asset 4,126,720
bytes (the two GMP archives). The guard's other side: the five crates built with the two variables unset (their build
scripts fetched their own copies): `check-build` refused all five (9 refusals); the same release build from a cache
whose circuits archive had one byte changed stopped in 0 s, before any build started.

How the build is made reproducible: a RISC Zero guest built without Docker would embed the absolute paths of its
sources; `scripts/guest-rustc` (cargo's `build.rustc-wrapper`) remaps them and replaces cargo's path-dependent
`-C metadata` in guest builds, so the image ids do not depend on where the tree is ([`image-ids.md`](image-ids.md)).
The release builds the guests with `scripts/reproduce-image-ids.sh` in place (LEZ v0.4.0-rc1 in `../upstream/` beside
the tree, the LEZ guests with their own RISC Zero home), so anyone can rebuild them with that script, or
`scripts/reproduce-image-ids.sh docker`, and compare. The tarball is made with fixed owner, order and modification
time. The vault is built from its sources alone into the release's own output directory; the deployment script
deploys only a tree whose forge build is byte-identical to the release's bytecode.

What is committed: `releases/VERSION/MANIFEST.json` and `releases/VERSION/SHA256SUMS`. The binaries are not
(their size, and they are build products); a release is published by attaching the tarball to a repository release,
which nothing here does (no publishing without the owner).

`scripts/release.sh verify DIR` (and `just release-verify DIR`) checks every line of `SHA256SUMS`, every file of
the manifest (size and sha256), that the CLI is the binary `check-build` passed, that the notices cover the native
code the manifest records and the crates of the release's lockfile and dependency set, that every crate with
symbols in the binary is listed (`nm`), the sources asset beside the directory, and, where `r0vm` 3.0.5 is
installed, recomputes the six programs' image ids (`r0vm --elf F --id`); without `r0vm` it says the ids were not
recomputed, and `--strict` (what `just release` uses) fails, as it does without `nm` or the sources asset. A build's
commit is `+dirty` when a tracked file differs or an untracked one exists (`scripts/release.sh commit`; cargo and the
build box use untracked files too). Tests: [`scripts/test_fetch_native.py`](../scripts/test_fetch_native.py) (22),
[`scripts/test_release_manifest.py`](../scripts/test_release_manifest.py) (24),
[`scripts/test_release_scripts.py`](../scripts/test_release_scripts.py) (13: the release path end to end with stub
cargo, forge, rustc, r0vm and nm, including review-fix-supply's failed-build case),
[`scripts/test_deny_all.py`](../scripts/test_deny_all.py) (13).

## 4. Deployment on testnet 0.4: one command

```sh
scripts/deploy-testnet.sh --release ferrata-X.Y.Z --lez <testnet 0.4 sequencer URL> \
  --evm-rpc <EVM JSON-RPC URL> --chain-id <id> --mode B --params <the testnet's parameters> \
  --wallet-home <LEZ wallet home> --payer <funded LEZ account> [--gas-rule eip8037] --send
```

`ferrata-X.Y.Z` stands for a release made with today's `release.sh` (with `BUILD-OK`, the check-build record and
the notices): the script's first step, `release.sh verify`, refuses release 0.1.0-rc.1. A new release is needed in
any case after the move to RISC Zero 3.1 ([`docs/design/risc0-3.1-migration.md`](design/risc0-3.1-migration.md)),
which changes the programs' image ids; none has been made yet. Without `--send` it prints every command and sends
nothing. In order:

1. **The release.** `release.sh verify`: every checksum, the manifest; the image ids it will deploy are printed.
2. **LEZ.** The endpoint must answer. With `--send`: LEZ's own `wallet` (the testnet's version), whose
   `wallet_config.json` must name the same sequencer (the script refuses another, and never edits a wallet's
   configuration), creates one public account per 96 KiB segment of each program (`MAX_SEGMENT_DATA_LEN`; LEZ allows
   at most 20) and its header, then `wallet program-loader deploy --elf ... --immutable` for the attestation program
   and the bridge program.
3. **The EVM chain.** The endpoint must report `--chain-id`; chain id 1 is always refused (prototype, unaudited).

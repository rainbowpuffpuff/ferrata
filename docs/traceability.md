# Ferrata: requirement traceability

This document maps every numbered requirement of Logos RFP-021 (Trustless Ethereum State Attestation for LEZ) and RFP-022 (Privacy-Preserving Wrapped ERC-20 and Ether Bridge for LEZ) to the Ferrata design, the evidence that exists today, and the milestone that delivers it. It follows the proposal and the bridge specification, [SPEC-v2](design/spec/bridge-spec-v2.md) as amended by [SPEC-v3](design/spec/bridge-spec-v3-changes.md) (D1–D13).

**Row counts, checked against the RFP texts: 64 rows for RFP-021 and 73 for RFP-022, soft requirements included (59 and 68 hard).**

## How to read the matrices

- **ID.** `F` Functionality, `U` Usability, `R` Reliability, `P` Performance, `S` Supportability, `VS` Verification Security (RFP-021), `Sec` Security (RFP-022), `Priv` Privacy Preservation (RFP-022), `Soft` soft requirements. Numbers follow the RFPs' own numbering inside each heading. In RFP-022, `S.n` (Supportability) and `Sec.n` (Security) are different lists.
- **Where.** The proposal section (§A1–§A8 for the attestation primitive, §B1–§B9 for the bridge) and the design note: `docs/design/attestation.md`, `docs/design/bridge.md`, `docs/design/lez-v0.4-findings.md`, or the finality analysis in `docs/design/finality-rule/{LEMMA,MODEL,RESULTS}.md`. Section names are written with "§"; milestone names (A1–A4, B1–B5) without.
- **Evidence today.** Only results that exist and were run, each with where it ran. Sources:
  - **[core]**: the `ferrata-core` README ([`crates/ferrata-core/README.md`](../crates/ferrata-core/README.md)). `cargo test --workspace`, native, on a laptop CPU.
  - **[bench]**: the core's RISC Zero 3.0.5 guest measurements ([`bench/RESULTS.md`](../bench/RESULTS.md); executor only, bare guests, not through LEZ).
  - **[lez]**: the LEZ v0.4.0-rc1 program results ([`lez/RESULTS.md`](../lez/RESULTS.md)). An **in-process harness** that runs the program through LEZ's own state machine (`lee`) and **copies** of LEZ's settlement functions, with real mainnet data; each transaction is settled in a block of its own at genesis base fees; no v0.4 sequencer ran. The private paths ran in RISC Zero dev mode, except two real proofs: a finality update on a laptop CPU (and, on an earlier image, on a GPU), and one private attestation on a GPU.
  - **[ckpt]**: the checkpoint program prototype (`ferrata-checkpoint`) README and results ([`checkpoint/`](../checkpoint/)). Rule (A) as built (SPEC-v2 §4.2 with SPEC-v3 D3), run in the RISC Zero 3.0.5 executor on LEZ blocks and Logos Blockchain inscriptions built with LEZ's and Logos Blockchain's own crates; private transactions in the fixtures carry filler proofs of real size. One one-block fixture (`cp-empty-1`) proven twice on a laptop CPU and wrapped to Groth16; the seal was **not** submitted to a contract. No LEZ or Logos Blockchain node was run. Rule (B) is **not built**.
  - **[vault]**: the `FerrataVault` v3 README and gas report ([`vault/`](../vault/); SPEC-v2 + SPEC-v3 D3–D5, D9). Foundry, **local EVM**, **mock verifier** behind RISC Zero's unmodified emergency-stop wrapper; 286 tests; not audited, not deployed. The D11 fixes and the D13 changes (watcher role, renounced stop owner, permissionless retirement after 30 days, protocol fees, the rule (B) path) are not in it.
  - **[release]**: the bridge v2 results ([`bridge/`](../bridge/)): `ferrata-bridge-core` v2 (native tests), the release and claim guests (RISC Zero 3.0.5, proven on a laptop CPU, Groth16 wrap on x86 with Docker), and the **previous (v2) vault** with RISC Zero's **real** `RiscZeroGroth16Verifier` (risc0-ethereum v3.0.0) in a **local EVM** (Foundry); the checkpoint proof is mocked there and no LEZ program ran.
  - **[sim]**: the finality-rule analysis, `docs/design/finality-rule/{LEMMA,MODEL,RESULTS}.md`: a written proof, a model of v0.4 sequencer and Logos Blockchain behaviour cited to source lines, and a simulator on that model (not a network).

  "none yet" means no test, measurement or artefact exists. *Estimate* marks a computed or projected figure, *derived* a figure computed from measured parts. Anything in the "How" column without evidence is designed, not built.
- **Named test or artefact.** The test file, test function, script or result table that an evidence source names for the row; "none yet" otherwise. The A4 and B5 gates require one named test per hard requirement, passing in CI.
- **Milestones** (from the proposal's milestone table): M0 go/no-go (both RFPs); A1 light client on LEZ v0.4; A2 attestation, reference consumers, private read; A3 attestation module, CLI, updater daemon, IDL; A4 attestation release candidate; B1 vault and inbound mint; B2 outbound (burn, checkpoint proof, release); B3 privacy suite, recovery, relayer, tenants, retirement; B4 bridge module, mini-app, admin view, CLI, daemon (the interfaces); B5 bridge release candidate; R audit remediation. "Stretch" means listed in the proposal as stretch.

## Requirements met only in part, or under a condition

**Both RFPs**

- **LEZ testnet 0.4 does not exist yet** (021: S.1; 022: S.1). `v0.4.0-rc1` is a release candidate. Until the testnet exists, deployment is to a standalone v0.4 sequencer with its block log published, recorded as a shortfall against both S.1 requirements; 021 F.7's "on testnet" waits on the same, and the return leg is then single-key.
- **No LEZ evidence comes from a sequencer** (021: F.1, F.7, F.8, S.2; 022: R.10). The LEZ program results run in an in-process harness over copies of LEZ's settlement functions; the private paths ran in dev mode apart from the real proofs of a finality update and of one private attestation. The checkpoint program ran on blocks built with LEZ's and Logos Blockchain's crates, with filler proofs in private transactions, and no node.
- **No machine at the declared minimum has been measured** (021: P.4; 022: P.4). Every proof so far ran on one 16-thread laptop CPU or on one cloud GPU (NVIDIA L4). The only laptop proof on the 021 side (a whole update, not a user attestation) peaked at 9.18 GiB, above the declared 8 GB; the one private attestation proven ran on the GPU. Release and claim-statement receipts took about 1.46 GB, but a full LEZ private claim, the 4-core minimum and macOS have not been measured.
- **SPEL IDL** (021: U.4; 022: U.4). SPEL's stable release targets LEZ v0.2.4; the IDL is hand-written and checked in CI until SPEL supports v0.4. Until then the IDL is not produced "using SPEL".
- **Audits** (021: S.8; 022: Sec.1). Procured separately and contracted by Logos; met only if that happens. Until the reports are published, the code is marked unfit for production.
- **M0 outcomes can narrow the scope.** If the private read fails, Logos decides whether to continue without 021 F.8's private path (also affecting 021 P.4's private attestation and R.11). If the private claim fails, Logos decides between public destinations only (022 F.4, U.6, Priv.7) and a raised minimum. If the token program cannot be pinned or ported, the bridge keeps balances itself or the client refuses composed burns.

**RFP-021**

- **F.7 and Soft.1, the bridge's own root.** The bridge's claim acts on `root(n)`, recorded by an earlier `ImportRoot` transaction: soft #1's recorded-statement pattern, in the bridge's own immutable form. F.7's same-transaction consumption is met by the attestation program's call path, not by this root; the generic recorded-statement path is stretch.
- **F.8, private consumption.** A private read keeps query, keys and account hidden, but is a public read: it shows which record was read, the consumer's program and that some transaction of it acted after that record. Tested in dev mode only.
- **F.9, checkpoint API.** `verify_checkpoint` ships in `ferrata_attest_module`; exposing it on the Logos Ethereum core module depends on the upstream pull request being accepted. It does not exist yet.
- **F.9, F.10, F.14, F.15: bound, successors, root ids, unscheduled forks.** Designed, not yet in the program (a fork in the schedule fixed at `Init` is crossed in place). A successor is accepted under the parent's root id only through `Init`'s three invariants.
- **F.5, same-address chain test.** Run in the in-process harness on real Sepolia data (Multicall3), not on a testnet deployment.
- **F.6, identifier semantics.** Storage and account identifiers omit the block, so an unchanged value read at two blocks shares one identifier; the block-number variant serves consumers that pin a block. Once-per-event consumers key on logs or accumulator leaves.
- **S.4, the Recommended Consumer Pattern.** It covers the RFP's four points and adds three rules; rule 1 (a secret committed in the attested fact) applies to deposits that carry one, as the vault's do.
- **U.6, reference consumers.** They attest the vault's deposit event; the vault refuses ETH without a commitment.
- **R.6, reuse.** BLS is reused (`blst`, upstream audited; zkcrypto as an unaudited cross-check). The light-client logic is Ferrata's own transcription, checked against official vectors, Helios and differential tests, and not yet audited.
- **R.7, liveness limit.** A finalised-only client stops if Ethereum finalises nothing for a whole sync-committee period; the instance is then replaced, which is a new trust decision.
- **U.3, Ethereum module light-client API.** Announced but not available; the updater uses `beacon_api_module` until it is.
- **P.1, P.2, P.3, attestation costs.** Attestation cycles are measured in bare guests, not through the program; per-attestation gas, proof time and size and the amortised tracking cost do not exist yet.
- **Soft.1, Soft.2, Soft.5.** No generic recorded-statement path and no general batching (stretch); the operator rebate is a design note and the protocol fee it would come from starts at zero.

**RFP-022**

- **Trust model ("no trust in signers, validators, …") and Security #7, on the return leg** (Trust model; F.7, Sec.6, Sec.7). On v0.4 the validity and finality of LEZ blocks can only come from the zone's accredited sequencers (`docs/design/lez-v0.4-findings.md`). An accepted burn root is valid unless an attacker controls *t* accredited keys of a key set the proof used (retired keys included) or the proof system is unsound.
  - **Rule (B), proposed:** met on that committee assumption. The root is also final unless Logos Blockchain reorganises deeper than *k*, or enough honest sequencers' nodes are eclipsed long enough to show them *k* private blocks, which is what a LEZ full node assumes. Off-chain roles are liveness-only. Rule (B) is specified, not built (signature checks *estimated* at 2.6–8.3M cycles), and needs each sequencer to run `ferrata_attestor`.
  - **Rule (A), the fallback:** met only within its four conditions (honest sequencers' nodes see *k* blocks in every two hours; at most *t* − 1 of the channel's live keys adversarial and honest blocks on chain within those turns plus a stall *S*; a random value unknown until a minute before it is recorded; `W ≥ 2 h + (t − 1) turns + S + 1 min`, enforced by the vault). Outside them the watchers are trusted for safety: [sim] none of 750 attack runs succeeded with the watcher's cancellation, and 724 of them succeeded without any guard (`docs/design/finality-rule/RESULTS.md`, table (j)); within them, 500 adversarial runs for committees of 3 to 16 showed no violation (table (i)); key rotation is argued, not simulated. (A) needs *t* + 1 live keys, so one silent sequencer stalls releases for *n* ≤ 5; the recommended committee is *n* ≥ 6.
  - Under both rules a *t*-key forgery is public for the whole wait; the release delay (24 h outside testnets) is a second window for revocation; an error not revoked within the revocation window halts the vault for good. On a single-sequencer testnet the leg rests on one key. If the checkpoint verifier is not ready, the release path ships against a test verifier and 022 F.7 is not met on testnet.
- **F.15, any EVM chain.** Holds for rule (B) generally, and for rule (A) only on chains with an unpredictable `prevrandao` (Ethereum and its testnets).
- **F.4, private-account minting.** Conditional on M0's private-claim check (see "M0 outcomes" above).
- **U.5, Priv.6, fee payer.** On v0.4 nobody can pay a private transaction's fee for a user. The relayer mitigation depends on the gas drop passing M0; otherwise a first claim needs native LEZ from a faucet or a public purchase, and the resulting correlation is documented.
- **F.13, fees.** Fees are charged in the wrapped token only; the rate is configurable within a 1% ceiling, the denomination is not. Only relay fees exist in the vault prototype.
- **F.10, F.14, admin and freeze libraries.** No v0.4 freeze library exists and the v0.4 admin port is in alpha: per-token freezing is bridge code, and the admin interface is in the program if the port is not released.
- **F.11, LEZ-side caps.** LEZ programs cannot read the clock; the LEZ caps use a caller-supplied monotone time that a sequencer can stretch.
- **U.1, wallet SDK.** The wallet SDK is not released; LEZ access goes through one adapter over `lez_core` (which pins v0.3.1, with v0.4 in open pull requests), to be switched within four weeks of the SDK's release.
- **S.2, P.4, Groth16 wrapping.** The wrap runs on x86 only (Docker; prover peak 7.32 GiB). macOS users prove the succinct receipt themselves and rely on a relayer or another x86 machine for the wrap; that party learns only what the release publishes, plus timing and network metadata.
- **P.6, checkpoint proving.** An idle LEZ hour proves faster than real time on the laptop (*extrapolated* about 34 min plus the wrap); an hour with 50 private transactions does not (*extrapolated* about 4.8 h); segments parallelise, and real recursion of composed segments was not run. M0 sets the thresholds.
- **R.4, Sec.8, Sec.9, entitlements across retirement and failure.** After a sunset, unimported deposits become refunds rather than claims, under D5's conditions. After the emergency stop, nothing more is released or refunded. Tokens not burned before a retirement lose their backing, a disclosed exception to R.4. The failsafe is stop-only and recovers no funds; the trust document lists which positions are lost per failure class.
- **Sec.6, supply.** Equals escrow less in-flight deposits and burns under the stated trust (committee and sequencer assumptions); a breach creates a shortfall of at most the caps before a freeze.
- **Privacy rests on RISC Zero's zero-knowledge property** (Priv.1–Priv.4). RISC Zero targets zero knowledge for its receipts without a written proof of it; every LEZ private transaction rests on the same property.
- **Soft.1, Soft.2, Soft.4.** Committed amounts need a new vault (stretch). The viewing key discloses burns only, not deposits or claims. No pluggable proof system: the verification path is immutable by design (Sec.8).
- **The prototypes trail the design.** The v3 vault implements SPEC-v3 D3–D5 and D9 with a mock verifier; the real verifier was measured in the previous (v2) vault. The D11 fixes and D13 changes (rule (B), watchers, renounced stop owner, permissionless retirement after 30 days, protocol fees, the independent `N_out`) are in the design, not in the prototypes. No LEZ-side bridge program (claim, burn, registry) exists yet.

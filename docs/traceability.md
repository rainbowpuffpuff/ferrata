# Ferrata: requirement traceability

This document maps every numbered requirement of Logos RFP-021 (Trustless Ethereum State Attestation for LEZ) and RFP-022 (Privacy-Preserving Wrapped ERC-20 and Ether Bridge for LEZ) to the Ferrata design, the evidence that exists today, and the milestone that delivers it. It follows the proposal and the bridge specification, [SPEC-v2](design/spec/bridge-spec-v2.md) as amended by [SPEC-v3](design/spec/bridge-spec-v3-changes.md) (D1–D13).

**Row counts, checked against the RFP texts: 64 rows for RFP-021 and 73 for RFP-022, soft requirements included (59 and 68 hard).**

## How to read the matrices

- **ID.** `F` Functionality, `U` Usability, `R` Reliability, `P` Performance, `S` Supportability, `VS` Verification Security (RFP-021), `Sec` Security (RFP-022), `Priv` Privacy Preservation (RFP-022), `Soft` soft requirements. Numbers follow the RFPs' own numbering inside each heading. In RFP-022, `S.n` (Supportability) and `Sec.n` (Security) are different lists.
- **Where.** The proposal section (§A1–§A8 for the attestation primitive, §B1–§B9 for the bridge) and the design note: `docs/design/attestation.md`, `docs/design/bridge.md`, `docs/design/lez-v0.4-findings.md`, or the finality analysis in `docs/design/finality-rule/{LEMMA,MODEL,RESULTS}.md`. Section names are written with "§"; milestone names (M0, A1–A4, B1–B4, R) without.
- **Evidence today.** Only results that exist and were run, each with where it ran. Sources:
  - **[core]**: the `ferrata-core` README ([`crates/ferrata-core/README.md`](../crates/ferrata-core/README.md)). `cargo test --workspace`, native, on a laptop CPU.
  - **[bench]**: the core's RISC Zero 3.0.5 guest measurements ([`bench/RESULTS.md`](../bench/RESULTS.md); executor only, bare guests, not through LEZ).
  - **[lez]**: the LEZ v0.4.0-rc1 program results ([`lez/RESULTS.md`](../lez/RESULTS.md)). An **in-process harness** that runs the program through LEZ's own state machine (`lee`) and **copies** of LEZ's settlement functions, with real mainnet data; each transaction is settled in a block of its own at genesis base fees. The private paths ran in RISC Zero dev mode, except two real proofs: a finality update on a laptop CPU (and, on an earlier image, on a GPU), and one private attestation on a GPU. **On a sequencer** ([`lez/live/`](../lez/live/README.md), [`lez/RESULTS.md`](../lez/RESULTS.md) §9): one recorded run of the program as it was before the attestation (image `cec0bc68…`) on LEZ's own unmodified v0.4.0-rc1 sequencer, inscribing on a Logos Blockchain node (one validator, leader proofs in dev mode), on a rented Linux container, receipts verified: the 65 harness transactions of that image had the same outcome there, 64 at the same execution gas, and a real proof of a private finality update, made against the live instance on the container's CPU, was verified and applied. One machine, not a network; recorded mainnet updates, not a live Ethereum stream; not in CI.
  - **[lab]**: the lab ([`lez/lab/README.md`](../lez/lab/README.md)): LEZ v0.4.0-rc1's own sequencer with one Logos Blockchain validator (leader proofs in dev mode), kept on Modal and driven every two hours, with two instances of the light-client program (Sepolia and mainnet) fed over the public job path; every session recorded and replayed offline (`lez/lab/lab.sh verify`). A local zone, not a testnet; no proofs.
  - **[lezbridge]**: the RFP-022 bridge program on LEZ v0.4.0-rc1 ([`lez/BRIDGE-RESULTS.md`](../lez/BRIDGE-RESULTS.md), plan [`lez/BRIDGE.md`](../lez/BRIDGE.md)). The [lez] harness, on a cloud container: a synthetic vault and records placed at genesis (and, in one test, blocks holding exactly the storage FerrataVault v5 wrote in a local EVM: §8a of the results), tokens registered from the vaults' storage (ETH in three denominations, a six-decimal token beside it), wrapped balances in the bridge's own accounts (no v0.4 token program is released); private claims and burns in RISC Zero dev mode in the tests, and one real proof each of a private claim (to a private account) and of a private burn on one NVIDIA L4, settled with the receipts verified on the build box (§7 of the results). Since branch `bridge-complete` the program has the registry, fees by leaf index, caps, freezes, roles and `Sunset` (§8 of the results), merged on branch `integration` with the Gloas header of the inbound crossing (image `f11b1aba…` at the integration path), whose private paths ran in dev mode only: the real proofs are of the program before them. No sequencer ran it: the stand-in crossing on a live sequencer (§11) deployed the frozen earlier program (`66722fc7…`).
  - **[ckpt]**: the checkpoint program prototype (`ferrata-checkpoint`) README and results ([`checkpoint/`](../checkpoint/)). Rule (A) as built (SPEC-v2 §4.2 with SPEC-v3 D3), run in the RISC Zero 3.0.5 executor on LEZ blocks and Logos Blockchain inscriptions built with LEZ's and Logos Blockchain's own crates; private transactions in the fixtures carry filler proofs of real size. One one-block fixture (`cp-empty-1`) proven twice on a laptop CPU and wrapped to Groth16; the seal was **not** submitted to a contract. No LEZ or Logos Blockchain node was run for these. Rule (B) (`checkpoint/guests/checkpoint-b`) and its runs over real LEZ blocks came later: [EVIDENCE](EVIDENCE.md) rows 16, 24, 63–68.
  - **[vault]**: the `FerrataVault` v5 README and gas report ([`vault/`](../vault/); SPEC-v2 + SPEC-v3 D3–D5, D9 and the vault items of D11 and D13, both finality rules). Foundry, **local EVM**, **mock verifier** behind RISC Zero's unmodified emergency-stop wrapper in its own suite; the 43 tests of `test/real/` (10 suites; 21 in v5's first runs, 15 in v3) run the return leg with RISC Zero's **real** verifier and real proofs of both programs, about a stand-in zone ([`e2e/`](../e2e/README.md)); not audited, not deployed. Built in v4: the rule (B) path (a real rule (B) proof verified, `test/real/RuleBReal.t.sol`), the D11 fixes, watchers, the 14-day role change, keyless retirement, the cap floor, refunds on the release bucket, nothing refunded after a stop. Built in v5: D13's fees (mint, relay, burn and checkpoint fees, the seven-day notice, schedules by leaf index, published for LEZ) and a deployment script that renounces the stop's owner, rehearsed on a local fork of Sepolia; 407 tests on branches `integration3` and `integration4` (396 on `integration`: 395 on `vault-fees` plus the export of its storage that the bridge program reads; then the real-block checkpoint's 10 and the privacy suite's Ethereum half), 223/223 planted bugs caught; with the fixes of the security review of 11 November (M-1, M-2, L-1, L-3, I-2, I-7), 433 tests on `integration5` (1 skipped there: the privacy suite's Ethereum half, which its script runs) and 254/254 planted bugs caught (branch `secfix-vault`, the same `src/`).
  - **[release]**: the bridge v2 results ([`bridge/`](../bridge/)): `ferrata-bridge-core` v2 (native tests), the release and claim guests (RISC Zero 3.0.5, proven on a laptop CPU, Groth16 wrap on x86 with Docker), and the **previous (v2) vault** with RISC Zero's **real** `RiscZeroGroth16Verifier` (risc0-ethereum v3.0.0) in a **local EVM** (Foundry); the checkpoint proof is mocked there and no LEZ program ran.
  - **[privacy]**: the privacy suite ([`docs/privacy/RESULTS.md`](privacy/RESULTS.md); `lez/harness/tests/privacy_suite.rs`, `vault/test/PrivacySuite.t.sol`, `scripts/privacy/`). 20 users' round trip through the [lezbridge] harness (private paths in **dev mode**, synthetic records) and the v3 vault (Foundry, **mock verifier**), on a cloud container; a differential gate over every public byte, an adversary, the field table against §B6, and seed-only recovery; and the same gate on **real proofs** of the final programs ([`docs/privacy/real/RESULTS.md`](privacy/real/RESULTS.md): 20 + 20 pairs proven on one L4, the releases checked by RISC Zero's Groth16 verifier in the vault, the receipts' and seals' bytes classified; the burn root's checkpoint still on the mock).
  - **[cli]**: the `ferrata` command-line tool ([`cli/README.md`](../cli/README.md)) over `ferrata-bridge-core`, the bridge wire, LEZ v0.4.0-rc1's own wallet library and alloy. Its end-to-end test ran on the Modal build box (CPU): the v5 vault on a **local anvil** (chain id 1) with the vault tests' **mock verifier** accepting the exact checkpoint and release journals (no real proof), and the zone in the [lezbridge] harness with the bridge guest in RISC Zero dev mode. Deposits, the scan and the status run through the binary; the claim, burns, release and recovery through the library functions the binary calls, with the harness in place of LEZ's sequencer client. Not run against a sequencer or a public network.
  - **[sim]**: the finality-rule analysis, `docs/design/finality-rule/{LEMMA,MODEL,RESULTS}.md`: a written proof, a model of v0.4 sequencer and Logos Blockchain behaviour cited to source lines, and a simulator on that model (not a network).
  - **[sectools]**: the security tools' note ([`notes/reviews/security/tools-2026-11-11.md`](../notes/reviews/security/tools-2026-11-11.md)): Slither 0.11.6, Aderyn 0.6.8 and Halmos 0.3.3 over `vault/src`, cargo-audit 0.23.0 and cargo-deny 0.20.2 over the Rust lockfiles, every finding triaged, on the **build box**. Tooling, not an audit.
  - **[fuzz]**: coverage-guided fuzzing of `ferrata-core` ([`fuzz/RESULTS.md`](../fuzz/RESULTS.md)): seven cargo-fuzz targets, native, on the **build box**.
  - **[verify]**: the reproducible-id check ([`guides/verify.md`](guides/verify.md), [`e2e/runs/verify-anyone/`](../e2e/runs/verify-anyone/README.md)): the crown run's six guests rebuilt at the crown build path on the **build box**.
  - **EVIDENCE row N**: a row of [`EVIDENCE.md`](EVIDENCE.md), which gives the measurement, where it ran, what is real and what stands in, and the command that reproduces it (rows 43–88 cover the modules, the CLIs, the daemons, the mini-app, the admin view and the IDL). "Remains" names what the row's requirement still needs, as README's "Specified but not built" lists it.

  "none yet" means no test, measurement or artefact exists. *Estimate* marks a computed or projected figure, *derived* a figure computed from measured parts. Anything in the "How" column without evidence is designed, not built.
- **Named test or artefact.** The test file, test function, script or result table that an evidence source names for the row; "none yet" otherwise. The A4 and B4 gates require one named test per hard requirement, passing in CI.
- **Milestones** (the milestone column follows the proposal's milestones; the proposal has no traceability tables of its own and points here): M0 open checks (both RFPs); A1 light client, production form; A2 attestation and reference consumers complete; A3 attestation module, CLI, updater, IDL; A4 testnet 0.4, attestation release; B1 return leg with several sequencers; B2 bridge on Sepolia, hardened, with privacy and recovery; B3 bridge module, mini-app, admin view, CLI, relayer; B4 testnet 0.4, bridge release; R audit remediation. The proposal's tables place RFP-021's soft 3 and 4 in A2 and its soft 1, 2 and 5 in A4, and RFP-022's soft 2 and 3 in B2; RFP-022's soft 4 is met by redeployment and migration (§B5, as Sec.8), and its soft 1 and 5 are not offered. A row saying "not planned" means no milestone builds it.

**RFP-021**

- **F.8, private consumption.** A private read keeps query, keys and account hidden, but is a public read: it shows which record was read, the consumer's program and that some transaction of it acted after that record. Tested in dev mode only.
- **F.9, checkpoint API.** `verify_checkpoint` is a method of `ferrata_attest_module` (EVIDENCE rows 59 and 105: it fetches the root from the beacon providers named in the call and the execution block from an execution endpoint, or through `eth_rpc_module`, which on Sepolia in `required` mode `verified_proxy_module` answered: [`modules/results/verified-proxy-2026-11-14/`](../modules/results/verified-proxy-2026-11-14/README.md)); exposing the check on the Logos Ethereum core module (`verified_proxy_module`, whose trusted block root is a checkpoint too) depends on an upstream pull request being accepted. That pull request is prepared, not opened, and that exposure does not exist yet.

Consumers bound to the root id are not built: the bridge, `ferrata_holdings` and the reference consumer still pin an instance ([README, "Specified but not built"](../README.md#specified-but-not-built)).
- **F.5, same-address chain test.** Run in the in-process harness on real Sepolia data (Multicall3), not on a testnet deployment.
- **F.6, identifier semantics.** Storage and account identifiers omit the block, so an unchanged value read at two blocks shares one identifier; the block-number variant serves consumers that pin a block. Once-per-event consumers key on logs or accumulator leaves.
- **S.4, the Recommended Consumer Pattern.** It covers the RFP's four points and adds three rules; rule 1 (a secret committed in the attested fact) applies to deposits that carry one, as the vault's do.
- **U.6, reference consumers.** They attest the vault's deposit event; the vault refuses ETH without a commitment.
- **R.6, reuse.** BLS is reused (`blst`, upstream audited; zkcrypto as an unaudited cross-check). The light-client logic is Ferrata's own transcription, checked against official vectors, Helios and differential tests, and not yet audited.
- **R.7, liveness limit.** A finalised-only client stops if Ethereum finalises nothing for a whole sync-committee period; the instance is then replaced, which is a new trust decision.
- **U.3, Ethereum module light-client API.** Announced but not available; the updater (a binary, EVIDENCE row 79, and a Logos module on its in-process chain, row 97) reads beacon nodes over HTTP, or through Logos Core's `beacon_api_module` (`lc_request`, the providers' JSON turned into SSZ: on Sepolia, on its in-process chain, [`modules/results/verified-proxy-2026-11-14/`](../modules/results/verified-proxy-2026-11-14/README.md)) until the API exists.

- **Soft.1, Soft.2, Soft.5.** No generic recorded-statement path and no general batching (not planned); the operator rebate is a design note and the protocol fee it would come from starts at zero.

**RFP-022**

- **Trust model ("no trust in signers, validators, …") and Security #7, on the return leg** (Trust model; F.7, Sec.6, Sec.7). On v0.4 the validity and finality of LEZ blocks can only come from the zone's accredited sequencers (`docs/design/lez-v0.4-findings.md`). An accepted burn root is valid unless an attacker controls *t* accredited keys of a key set the proof used (retired keys included) or the proof system is unsound.
  - **Rule (B), proposed:** met on that committee assumption. The root is also final unless Logos Blockchain reorganises deeper than *k*, or enough honest sequencers' nodes are eclipsed long enough to show them *k* private blocks, which is what a LEZ full node assumes. Off-chain roles are liveness-only. Rule (B) is built and proven over real LEZ blocks (EVIDENCE rows 24, 63–68; 1.69M cycles per attestor, row 16; t = 3 of a real zone of four sequencers accepted by the v5 vault through RISC Zero's verifier, row 65), and needs each sequencer to run `ferrata_attestor` (built as a program and as a Logos module, which ran beside each sequencer of a running zone of four without the bridge program, row 95).
  - **Rule (A), the fallback:** met only within its four conditions (honest sequencers' nodes see *k* blocks in every two hours; at most *t* − 1 of the channel's live keys adversarial and honest blocks on chain within those turns plus a stall *S*; a random value unknown until a minute before it is recorded; `W ≥ 2 h + (t − 1) turns + S + 1 min`, enforced by the vault). Outside them the watchers are trusted for safety: [sim] none of 750 attack runs succeeded with the watcher's cancellation, and 724 of them succeeded without any guard (`docs/design/finality-rule/RESULTS.md`, table (j)); within them, 500 adversarial runs for committees of 3 to 16 showed no violation (table (i)); key rotation is argued, not simulated. (A) needs *t* + 1 live keys, so one silent sequencer stalls releases for *n* ≤ 5; the recommended committee is *n* ≥ 6.
  - Under both rules a *t*-key forgery is public for the whole wait; the release delay (24 h outside testnets) is a second window for revocation; a wrong checkpoint not revoked within the revocation window (7 days by default) halts the vault for good: `revokeFrom` then refuses it, every later candidate must descend from the finalised state (`submitCandidate` reverts `ParentNotFinal` otherwise), so no honest checkpoint, release or refund can follow; freezes and the checkpoint pause only delay and expire (`docs/design/bridge.md` §10.5, §10.6, "The halt"; `docs/trust.md`, "The halt"). On a single-sequencer testnet the leg rests on one key. If the checkpoint verifier is not ready, the release path ships against a test verifier and 022 F.7 is not met on testnet.
- **F.15, any EVM chain.** Holds for rule (B) generally, and for rule (A) only on chains with an unpredictable `prevrandao` (Ethereum and its testnets).
- **F.4, private-account minting.** Conditional on M0's private-claim check (see "M0 outcomes" above).
- **U.5, Priv.6, fee payer.** On v0.4 nobody can pay a private transaction's fee for a user. The relayer mitigation depends on the gas drop passing M0; otherwise a first claim needs native LEZ from a faucet or a public purchase, and the resulting correlation is documented.
- **F.13, fees.** Fees are charged in the wrapped token only; the rate is configurable within a 1% ceiling, the denomination is not. The vault prototype (v5) charges all four fees; the bridge program on LEZ imports the vault's fee schedules (`ImportFees`) and pays a claim's relay and mint fees ([`lez/BRIDGE-RESULTS.md`](../lez/BRIDGE-RESULTS.md)).
- **F.10, F.14, admin and freeze libraries.** No v0.4 freeze library exists and the v0.4 admin port is in alpha: per-token freezing is bridge code, and the admin interface is in the program if the port is not released.
- **F.11, LEZ-side caps.** LEZ programs cannot read the clock on v0.4.0-rc1 and rc2 (on rc3 they can read the block producer's timestamp, rounded, which one producer sets: [`lez/results/v0.4.0-rc3/README.md`](../lez/results/v0.4.0-rc3/README.md)); the LEZ caps and freezes run on the newest Ethereum execution timestamp the attestation program recorded, never on a caller's time (EVIDENCE row 28).
- **U.1, wallet SDK.** The wallet SDK is not released; LEZ access goes through one adapter over `lez_core` (on LEZ v0.4.0-rc1 since 13 November; the bridge module's LEZ reads and its private claim and burn already go through it, with a patch of ours, EVIDENCE rows 113-114), to be switched within four weeks of the SDK's release.
- **S.2, P.4, Groth16 wrapping.** The wrap runs on x86 only (Docker; prover peak 7.32 GiB). macOS users prove the succinct receipt themselves and rely on a relayer or another x86 machine for the wrap; that party learns only what the release publishes, plus timing and network metadata.
- **P.6, checkpoint proving.** An idle LEZ hour proves faster than real time on the laptop (*extrapolated* about 34 min plus the wrap); an hour with 50 private transactions does not (*extrapolated* about 4.8 h); segments parallelise, and real recursion of composed segments was not run. M0 sets the thresholds.
- **R.4, Sec.8, Sec.9, entitlements across retirement and failure.** After a sunset, unimported deposits become refunds rather than claims, under D5's conditions. After the emergency stop, nothing more is released or refunded. Tokens not burned before a retirement lose their backing, a disclosed exception to R.4. The failsafe is stop-only and recovers no funds; the trust document lists which positions are lost per failure class.
- **Sec.6, supply.** Equals escrow less in-flight deposits and burns under the stated trust (committee and sequencer assumptions); a breach creates a shortfall of at most the caps before a freeze.
- **Privacy rests on RISC Zero's zero-knowledge property** (Priv.1–Priv.4). RISC Zero targets zero knowledge for its receipts without a written proof of it; every LEZ private transaction rests on the same property.
- **Soft.1, Soft.2, Soft.4.** Committed amounts need a new vault (not planned). The viewing key discloses burns only, not deposits or claims. No pluggable proof system: the verification path is immutable by design (Sec.8).

The watchers' `monitor`, `ferrata_attestor` and the independent `N_out` are in the design, not in the prototypes. No LEZ-side bridge program (claim, burn, registry) exists yet.

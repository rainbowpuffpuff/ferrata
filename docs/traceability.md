# Ferrata: requirement traceability

This document maps every numbered requirement of Logos RFP-021 (Trustless Ethereum State Attestation for LEZ) and RFP-022 (Privacy-Preserving Wrapped ERC-20 and Ether Bridge for LEZ) to the Ferrata design, the evidence that exists today, and the milestone that delivers it. It follows the proposal and the bridge specification, [SPEC-v2](design/spec/bridge-spec-v2.md) as amended by [SPEC-v3](design/spec/bridge-spec-v3-changes.md) (D1–D13).

**Row counts, checked against the RFP texts: 64 rows for RFP-021 and 73 for RFP-022, soft requirements included (59 and 68 hard).**

"Shown" means every clause is demonstrated today by a named test or a recorded run on real code (LEZ v0.4 release candidates' own state machine or a sequencer we ran, a local EVM or Sepolia); "waits on Logos" means the requirement names LEZ testnet 0.4 or another upstream component that is not released. The soft requirements, counted apart: RFP-021 5 shown; RFP-022 2 shown, 3 in part.

## How to read the matrices

- **ID.** `F` Functionality, `U` Usability, `R` Reliability, `P` Performance, `S` Supportability, `VS` Verification Security (RFP-021), `Sec` Security (RFP-022), `Priv` Privacy Preservation (RFP-022), `Soft` soft requirements. Numbers follow the RFPs' own numbering inside each heading. In RFP-022, `S.n` (Supportability) and `Sec.n` (Security) are different lists.
- **Where.** The proposal section (§A1–§A8 for the attestation primitive, §B1–§B9 for the bridge) and the design note: `docs/design/attestation.md`, `docs/design/bridge.md`, `docs/design/lez-v0.4-findings.md`, or the finality analysis in `docs/design/finality-rule/{LEMMA,MODEL,RESULTS}.md`. Section names are written with "§"; milestone names (M0, A1–A4, B1–B4, R) without.

  "none yet" means no test, measurement or artefact exists. *Estimate* marks a computed or projected figure, *derived* a figure computed from measured parts. Anything in the "How" column without evidence is designed, not built.
- **Named test or artefact.** The test file, test function, script or result table that an evidence source names for the row; "none yet" otherwise. The A4 and B4 gates require one named test per hard requirement, passing in CI.
- **Milestones** (the milestone column follows the proposal's milestones; the proposal has no traceability tables of its own and points here): M0 open checks (both RFPs); A1 light client, production form; A2 attestation and reference consumers complete; A3 attestation module, CLI, updater, IDL; A4 testnet 0.4, attestation release; B1 return leg with several sequencers; B2 bridge on Sepolia, hardened, with privacy and recovery; B3 bridge module, mini-app, admin view, CLI, relayer; B4 testnet 0.4, bridge release; R audit remediation. A row saying "not planned" means no milestone builds it.

- **LEZ's check of private-transaction receipts** (021: F.1, F.2, F.12, S.6, VS.1, VS.2, VS.5, VS.6; 022: Sec.2, Sec.3, Sec.6). LEZ v0.4.0-rc1 and rc3 verify a privacy-preserving transaction's receipt with risc0-zkvm 3.0.5 and accept any receipt kind, Groth16 included (GHSA-g6qg-9j8p-7j87; whether a forged one passes is for Logos to confirm, and we built none). LEZ applies a private transaction's calls to public actors on its proof alone, with the sender its journal names, so every Ferrata program's public state rests on that check; the attestation program, the bridge program and the reference consumer also accept some such calls on the sender's program alone. A forged receipt LEZ accepted could write an instance's store and records (`ApplyVerified`, or `Apply` and `Record` in a job's or the instance's name), which public consumers read; nothing in Ferrata's programs removes this ([trust](trust.md) §5; [security note](security/risc0-groth16-advisory-2026-11-21/README.md), its correction of 23 November 2026).

**RFP-021**

- **F.7 and Soft.1, the bridge's own root.** The bridge's claim acts on `root(n)`, recorded by an earlier `ImportRoot` transaction: soft #1's recorded-statement pattern, in the bridge's own immutable form. F.7's same-transaction consumption is met by the attestation program's call path, not by this root; the generic recorded-statement path is built beside it as `ferrata_statements`, not deployed (EVIDENCE row 155).
- **F.8, private consumption.** A private read keeps query, keys and account hidden, but is a public read: it shows which record was read, the consumer's program and that some transaction of it acted after that record. The byte searches ran in dev mode; the private attestation itself was proven for real on a GPU, on CPUs and on LEZ v0.4.0-rc3's sequencer (EVIDENCE rows 5, 32, 123). The F.8 two-deposit full-diff test is built and passes in dev mode (row 152).
- **F.9, checkpoint API.** `verify_checkpoint` is a method of `ferrata_attest_module` (EVIDENCE rows 59 and 105: it fetches the root from the beacon providers named in the call and the execution block from an execution endpoint, or through `eth_rpc_module`, which on Sepolia in `required` mode `verified_proxy_module` answered: [`modules/results/verified-proxy-2026-11-14/`](../modules/results/verified-proxy-2026-11-14/README.md)); exposing the check on the Logos Ethereum core module (`verified_proxy_module`, whose trusted block root is a checkpoint too) depends on an upstream pull request being accepted. That pull request is prepared, not opened, and that exposure does not exist yet.
- **F.9, F.10, F.14, F.15: bound, successors, root ids, unscheduled forks.** In the program (EVIDENCE rows 69, 70): a fork in the schedule fixed at `Init` is crossed in place, one added later by a successor, accepted under the parent's root id only through `Succeed`'s three invariants. Consumers bound to the root id are not built: the bridge, `ferrata_holdings` and the reference consumer still pin an instance ([README, "Specified but not built"](../README.md#specified-but-not-built)).
- **F.5, same-address chain test.** Run in the in-process harness on real Sepolia data (Multicall3), not on a testnet deployment. The same-address contract is attested under the Sepolia record only; its mainnet side is its code hash from a fixture (`lez/harness/src/sepolia.rs:279`, `:442-485`), and the mainnet-to-Sepolia refusal is on WETH.
- **F.6, identifier semantics.** Storage and account identifiers omit the block, so an unchanged value read at two blocks shares one identifier; the block-number variant serves consumers that pin a block. Once-per-event consumers key on logs or accumulator leaves; the statement class says which identifiers those are (`docs/design/attestation.md` §5.7).
- **S.4, the Recommended Consumer Pattern.** It covers the RFP's four points and adds three rules; rule 1 (a secret committed in the attested fact) applies to deposits that carry one, as the vault's do.
- **U.6, reference consumers.** The ERC-20 consumer attests a plain `Transfer` log; the native-ETH consumer attests the vault's deposit event, since a plain ETH transfer leaves no log and the vault refuses ETH without a commitment (EVIDENCE row 73).
- **R.6, reuse.** BLS is reused (`blst`, upstream audited; zkcrypto as an unaudited cross-check). The light-client logic is Ferrata's own transcription, checked against official vectors, Helios, Lodestar's light client and differential tests, and not yet audited.
- **R.7, liveness limit.** A finalised-only client stops if Ethereum finalises nothing for a whole sync-committee period, and an instance left past its weak-subjectivity bound refuses every update (EVIDENCE rows 69, 70); in both cases the instance is replaced, which is a new trust decision. The live run met the second case: its `Init` from a 38-day-old checkpoint was refused and a fresh checkpoint was used (row 91).
- **U.3, Ethereum module light-client API.** Announced but not available; the updater (a binary, EVIDENCE row 79, and a Logos module on its in-process chain, row 97) reads beacon nodes over HTTP, or through Logos Core's `beacon_api_module` (`lc_request`, the providers' JSON turned into SSZ: on Sepolia, on its in-process chain, [`modules/results/verified-proxy-2026-11-14/`](../modules/results/verified-proxy-2026-11-14/README.md)) until the API exists.
- **P.1, P.2, P.3, attestation costs.** Cycles per attestation are measured through the program on real mainnet blocks (P.1's evidence); the amortised tracking cost with real proving does not exist yet ([performance](performance.md), "Gaps").
- **Soft.1, Soft.2, Soft.5.** The recorded-statement path and the operator rebate are built and tested in the harness, not deployed (EVIDENCE rows 155, 156); a rebate pool is funded by whoever chooses to, and funding it from the bridge's wrapped fee tokens needs a conversion that is not built (the protocol fee starts at zero). No general batching across consumers (not planned).

**RFP-022**

- **Trust model ("no trust in signers, validators, …") and Security #7, on the return leg** (Trust model; F.7, Sec.6, Sec.7). On v0.4 the validity and finality of LEZ blocks can only come from the zone's accredited sequencers (`docs/design/lez-v0.4-findings.md`). An accepted burn root is valid unless an attacker controls *t* accredited keys of a key set the proof used (retired keys included) or the proof system is unsound.
  - **Rule (B), proposed:** met on that committee assumption. The root is also final unless Logos Blockchain reorganises deeper than *k*, or enough honest sequencers' nodes are eclipsed long enough to show them *k* private blocks, which is what a LEZ full node assumes. Off-chain roles are liveness-only, apart from the attestors and the LEZ and Logos Blockchain nodes they read. Rule (B) is built and proven over real LEZ blocks (EVIDENCE rows 24, 63–68; 1.69M cycles per attestor, row 16; t = 3 of a real zone of four sequencers accepted by the v5 vault through RISC Zero's verifier, row 65), and needs each sequencer to run `ferrata_attestor` (built as a program and as a Logos module, which ran beside each sequencer of a running zone of four without the bridge program, row 95; as a program it ran beside each sequencer of the zone that carried the bridge program, whose burns were released through a vault on a local anvil, rows 100, 101). The live Sepolia round trips used rule (B) with n = t = 1 (rows 41, 91).
  - **Rule (A), the fallback:** met only within its four conditions (honest sequencers' nodes see *k* blocks in every two hours; at most *t* − 1 of the channel's live keys adversarial and honest blocks on chain within those turns plus a stall *S*; a random value unknown until a minute before it is recorded; `W ≥ 2 h + (t − 1) turns + S + 1 min`, enforced by the vault). Outside them the watchers are trusted for safety: [sim] none of 750 attack runs succeeded with the watcher's cancellation, and 724 of them succeeded without any guard (`docs/design/finality-rule/RESULTS.md`, table (j)); within them, 500 adversarial runs for committees of 3 to 16 showed no violation (table (i)); key rotation is argued, not simulated. (A) needs *t* + 1 live keys, so one silent sequencer stalls releases for *n* ≤ 5; the recommended committee is *n* ≥ 6.
  - Under both rules a *t*-key forgery is public for the whole wait; the release delay (24 h outside testnets) is a second window for revocation; a wrong checkpoint not revoked within the revocation window (7 days by default) halts the vault for good: `revokeFrom` then refuses it, every later candidate must descend from the finalised state (`submitCandidate` reverts `ParentNotFinal` otherwise), so no honest checkpoint, release or refund can follow; freezes and the checkpoint pause only delay and expire (`docs/design/bridge.md` §10.5, §10.6, "The halt"; `docs/trust.md`, "The halt"). On a single-sequencer testnet the leg rests on one key. If the checkpoint verifier is not ready, the release path ships against a test verifier and 022 F.7 is not met on testnet.
- **F.15, any EVM chain.** Holds for rule (B) generally, and for rule (A) only on chains with an unpredictable `prevrandao` (Ethereum and its testnets).
- **F.4, private-account minting.** Conditional on M0's private-claim check (see "M0 outcomes" above); the private claim was proven for real and applied by LEZ v0.4.0-rc3's sequencer (EVIDENCE row 123).
- **U.5, Priv.6, Priv.7, fee payer.** On v0.4 nobody can pay a private transaction's fee for a user. The relayer mitigation is the gas drop, which passed M0's check on LEZ v0.4.0-rc3 (EVIDENCE row 124, one local validator; the relayer daemon's sealed credit and the tool's claim since on LEZ v0.4.0-rc1's sequencer with dev-mode proofs, row 205; burns with a drop are not shown); otherwise a first claim needs native LEZ from a faucet or a public purchase, and the resulting correlation is documented. U.5 and Priv.7 are in part for it: the gas drop is on only once the user names a relayer's inbox (`--gas-drop-inbox`), and the tool's default line says the fee payer's native LEZ can link the claim to the user (`cli/src/flow.rs:516`).
- **F.13, fees.** Fees are charged in the wrapped token only; the rate is configurable within a 1% ceiling, the denomination is not. The vault prototype (v5) charges all four fees; the bridge program on LEZ imports the vault's fee schedules (`ImportFees`) and pays a claim's relay and mint fees ([`lez/BRIDGE-RESULTS.md`](../lez/BRIDGE-RESULTS.md)).
- **U.9, the mini-app's endpoints** (in part). Inside Logos Core the view switches the LEZ sequencer only through the chain service, the stand-in for Logos Core's LEZ module.
- **F.10, F.14, admin and freeze libraries.** No v0.4 freeze library exists and the v0.4 admin port is in alpha: per-token freezing is bridge code, and the admin interface is in the program if the port is not released.
- **F.11, LEZ-side caps.** LEZ programs cannot read the clock on v0.4.0-rc1 and rc2 (on rc3 they can read the block producer's timestamp, rounded, which one producer sets: [`lez/results/v0.4.0-rc3/README.md`](../lez/results/v0.4.0-rc3/README.md)); the LEZ caps and freezes run on the newest Ethereum execution timestamp the attestation program recorded, never on a caller's time (EVIDENCE row 28).
- **U.1, wallet SDK.** The wallet SDK is not released; LEZ access goes through one adapter over `lez_core` (on LEZ v0.4.0-rc1 since 13 November; the bridge module's LEZ reads and its private claim and burn already go through it, with a patch of ours, EVIDENCE rows 113-114), to be switched within four weeks of the SDK's release.
- **S.2, P.4, Groth16 wrapping.** The wrap runs on x86 only (Docker; prover peak 7.32 GiB). macOS users prove the succinct receipt themselves and rely on a relayer or another x86 machine for the wrap; that party learns only what the release publishes, plus timing and network metadata.
- **P.6, checkpoint proving.** An idle LEZ hour proves faster than real time on the laptop (*extrapolated* about 34 min plus the wrap); an hour with 50 private transactions does not (*extrapolated* about 4.8 h); segments parallelise, and real recursion of composed segments was not run. M0 sets the thresholds.
- **R.4, Sec.8, Sec.9, entitlements across retirement and failure.** After a sunset, unimported deposits become refunds rather than claims, under D5's conditions. After the emergency stop, nothing more is released or refunded. Tokens not burned before a retirement lose their backing, a disclosed exception to R.4. The failsafe is stop-only and recovers no funds; the trust document lists which positions are lost per failure class.
- **Sec.6, supply.** Equals escrow less in-flight deposits and burns under the stated trust (committee and sequencer assumptions); a breach creates a shortfall of at most the caps before a freeze.
- **Privacy rests on RISC Zero's zero-knowledge property** (Priv.1–Priv.4). RISC Zero targets zero knowledge for its receipts without a written proof of it; every LEZ private transaction rests on the same property.
- **Soft.1, Soft.2, Soft.4.** Committed amounts need a new vault on either leg; the path is documented, not built (`docs/design/committed-amounts.md`). A disclosure document covers deposits and claims as well as burns, wallet-side (EVIDENCE row 157); no disclosure of a link leaves other users' anonymity sets untouched. The proof system is pluggable per deployment: the vault takes its verifier and image ids as constructor parameters, and adopting another proof system is a new vault and a migration (Sec.8); the second proof system tested is a mock (`vault/test/mocks/MockVerifierB.sol`).
- **The prototypes trail the design.** The v5 vault implements SPEC-v3 D3–D5, D9 and the vault items of D11 and D13 with both finality rules, including D13's fees; its own suite uses a mock verifier, and `test/real/` verifies real proofs of both checkpoint rules and of the release program, about a stand-in zone built with test keys, except the rule (B) checkpoints over real LEZ blocks: 195 blocks of the lab's devnet (one validator, dev-mode leader proofs, n = 1, no burns; `checkpoint/RESULTS.md`, "Real LEZ blocks"; EVIDENCE row 24), a zone of four sequencers without the bridge program (row 65), and zones of four and five sequencers carrying the bridge program and its burns (rows 100, 101). Built since this section was first written: the LEZ-side bridge program with claims, burns, the registry, fees, caps, freezes, roles and `Sunset` (rows 8–11, 74), the watchers' `monitor` (rows 43–45), `ferrata_attestor` (row 63) and the burn-index-independent `N_out` (row 30).

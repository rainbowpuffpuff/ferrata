# Ferrata security audit scope

**Project-authored scope for quotation by an independent auditor.** It defines the audit requested by RFP-021 Supportability #8 (consensus and inclusion logic before production, report published) and RFP-022 Security #1 (both blockchain contracts before any mainnet deployment, report published). Their status is **not yet**, and Logos contracting the audit is a condition (`docs/requirements-status.md:124`, `:237`; `docs/traceability.md:123`, `:234`). References are repository-relative; `:a-b` means a line range in the last file named.

The two engagements overlap. RFP-022 includes the attestation primitive it consumes, so the RFP-022 table repeats the RFP-021 files; **do not add the totals**. The unit of review is the source and configuration at the commit supplied with this document, with any later audit-fix commit identified separately.

## 1. Reproducible source inventory

Run from the repository root:

```sh
git rev-parse HEAD
git ls-files
python3 -I scripts/audit_scope.py
python3 -I scripts/test_audit_scope.py
```

The standard-library generator selects only tracked `.rs`/`.sol` paths under the production prefixes below and parses the named lockfiles. It counts physical lines with `splitlines()`: nonblank lines containing code are **Code** (including code followed by a comment), comment-only lines are **Comments**, and the remainder are **Blank**. Nested block comments and quoted strings are skipped when classifying comments. Total is the sum of the three. These are source-size measures, not effort estimates, and exclude all dependency source.

Differential agreement with alloy-trie/alloy-rlp likewise does not remove the handwritten parsers from scope (`docs/traceability.md:90`).

### 1.4 Explicit exclusions

- **Out of the deployed boundary:** CLI and `bridge/crates/ferrata-disclose`, Logos modules, UI and `site/`/`web/`, updaters, relayers, monitors, GPU/host provers, benchmarks, deployment and test-network scripts. They operate off chain or prepare inputs and cannot mutate the deployed verifier/image configuration (`docs/requirements-status.md:244`). Their confidentiality, liveness and operational safety need a separate review; excluding them is not a finding that they are harmless.
- **Tests and evidence:** tests, harnesses, fuzz targets/corpora, vectors, review notes and recorded runs support assurance but are not production artifacts. `vault/test`, `vault/src/standin`, `checkpoint/fidelity`, `lez/harness` and `e2e` are excluded. In particular, the stand-in checkpoint verifier trusts operator keys and is expressly not production (`docs/trust.md:458-482`).
- **Other programs:** reference/holdings consumers, scripted tests, statements/rebate, names/messages, the experimental residue and all `lez-v03*` ports. They are not the attestation or bridge programs named here. Micro/plain checkpoint benchmarks and standalone `claim`/`gasdrop` guests are not verified by this vault; the guests the current vault verifies and the auxiliary guests' phase distinction are listed at `docs/image-ids.md:64-70`. Shared bridge-core code remains included. A deployment that makes either auxiliary guest authoritative must add it and its caller to scope.
- **Upstream implementations:** dependencies in §1.3 and LEZ itself are not counted as Ferrata-authored code. Review their Ferrata integration and security assumptions here; quote a separate upstream audit if their internals must be re-audited.

### 3.2 Known open items and questions to start from

1. **OPEN-1 — LEZ private-receipt boundary (safety-critical).** LEZ rc1/rc3 use `risc0-zkvm 3.0.5` in the GHSA-g6qg-9j8p-7j87 range. Whether a forged Groth16 receipt passes LEZ has **not been tested**; LEZ replays private-to-public calls using journal-named senders, so a bypass could affect public attestation and bridge state, including `issue` and burn delivery (`docs/trust.md:568-620`; `docs/traceability.md:277`). Confirm with Logos, test malicious receipt forms on the exact runtime, and do not assume Ferrata sender checks repair an upstream soundness failure.
2. **OPEN-2 — actual guest BLS and actor shell.** Differential tests run native upstream `blst 0.3.17`, not the `rv32im` ELF with RISC Zero's `blst` patch; their program shell is a mirror, not the deployed binary (`crates/ferrata-spectests/HELIOS-DIFFERENTIAL.md:198-209`). Exercise the accelerated guest, PDA derivation, actor authorization, validity-window clock, write-once accounts and private/public boundaries on LEZ itself.
3. **OPEN-3 — disclosed vault/bridge behaviours.** A deposit after a tripped verifier stop can be stranded; a zero or too-small release-cap floor can block releases/refunds; a nested `Transfer` in a holder-authorized transaction can move that holder's balance (`docs/reviews/agent-review-vault-guests-2026-11-16.md:29-136`, disposition `:447-458`). Determine whether documentation/deployment checks sufficiently mitigate these or whether new artifacts are required before production.
4. **OPEN-4 — other unfixed review decisions.** Release-time rather than burn-time outbound fees; plaintext-claim relay-fee copying; no `maxTotal` on ERC-20 deposits; sequencer-clock reliance for the attestation validity window; and live-threshold rotation stalls remain expressly not fixed (`docs/reviews/security/fixes-2026-11-11.md:17-29`). Separately evaluate fee-schedule range correlation (`docs/reviews/redteam-2026-11-18.md:99-108`) and deployment acceptance of single-key committees/unbounded or unsuitable parameters (`docs/trust.md:53`; `docs/reviews/agent-review-vault-guests-2026-11-16.md:180-187`).
5. **OPEN-5 — real-proof coverage is asymmetric.** Under verifier 3.1, rule (B) has real-seal tests but rule (A) does not; the LEZ side still awaits RISC Zero 3.1 (`docs/requirements-status.md:238-239`). Whether 3.1.0 itself has audit coverage is not established (`:204`). The latest B1 migration was not rerun after the burn-tag rebuild (`:244`), real-proof privacy records predate B1 (`:251-252`), and the combined supply runs still use mock verification and synthetic storage (`:242`). Treat those as explicit residual test gaps, not failures of the properties.
6. **OPEN-6 — finality assumptions and operational realization.** Rule (B)'s real proof predates the tip-inscription check, and a Logos-operated rule (B) zone with per-sequencer attestors is still absent (`docs/trust.md:387-402`). Rule (A) needs F1–F4 or live uneclipsed watchers, and rule (A)'s rotation/key simulations have limits (`:404-433`). Validate the exact committee, Bedrock layout, wait/release-delay and watcher configuration proposed for deployment.
7. **OPEN-7 — scope change control.** B1 is not byte-identical to earlier deployed bridge programs, and no current-vault audit can be inherited from evidence about earlier images (`docs/image-ids.md:9-19`, `:111-136`). Rebuild and compare the reviewed artifacts using the recorded commands (`docs/image-ids.md:75-83`, `:102-104`), and re-scope every code, dependency or deployment-parameter change.

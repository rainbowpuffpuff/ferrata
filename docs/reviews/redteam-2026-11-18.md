# Blind red team of the light client and the bridge, 18 November 2026

340 adversarial vectors and positive controls, written from the specification **before anyone read the
implementation**, then run through the real programs. Result: **317 PASS, 9 MISMATCH, 2 PANIC, 10
UNSUPPORTED, 2 HARNESS-ERROR**; one finding in a program (F1, low), one privacy observation (O1) and
one error-code ambiguity (O2); every other mismatch is a vector error, each with its evidence below.
Not audited; the vectors complement, and do not replace, the audit the proposal plans.

## Protocol

1. **Phase 1, blind** (16:51 to 17:06 CET): the vectors were written from Logos's RFP-021 and RFP-022
   texts, consensus-specs `v1.7.0-beta.4`'s light-client and BLS rules, Ferrata's specification
   documents and the wire types and codes only; the files read, and one disclosed slip (the bodies of five
   check functions of `lez/bridge-wire/src/lib.rs` displayed by a filter error), are listed in
   [`vectors/redteam-2026-11-18/README.md`](../../vectors/redteam-2026-11-18/README.md), "Blindness".
   They were committed alone, as `redteam: phase 1, blind vectors`, commit
   `e8d4f6809168f0364879c94a5c25027a36e67569` at **2026-11-18T17:06:46+01:00**: that commit's time is the
   evidence of blindness; no implementation file was opened before it.
2. **Phase 2**: each vector is run by a test that builds its setup from real fixtures (mainnet periods
   1899–1903, Sepolia through Gloas, the mainnet attestation fixtures, FerrataVault v5's deposits) or,
   where a vector needs keys no real committee gives out, from a synthetic chain whose committee the test
   holds (`ferrata_spectests::testkit`), applies its mutation, and records what the program did. The
   expectations are read from the committed `vectors.json` and never edited; code names resolve to
   numbers through the crates' own tables (`lez/harness/tests/redteam_common/mod.rs`).
3. **Verdicts**: PASS (the outcome matches; for a refusal, a code the vector lists), MISMATCH,
   PANIC (refused without a code where the specification names one), UNSUPPORTED (not expressible with the
   fixtures, or not implemented in this run), HARNESS-ERROR (the test's own setup failed: no verdict).
   Every mismatch is classified: a **program bug** (a finding; programs are not changed here), a
   **specification ambiguity**, or a **vector error**.

Where it ran: the Modal build box (16 cores), LEZ v0.4.0-rc1's state machine in the in-process harness,
`RISC0_DEV_MODE=1` (executed, not proven); the vault under forge (Foundry 1.3.6); the checkpoint core
natively. No program, guest or image id was changed; the harness gained `#[derive(Clone)]` on `Chain` and
`scenarios::World` only.

## Findings

**F1 (program, low): the LEZ bridge's `Init` accepts a configuration whose freeze authority is its admin.**
BR-INIT-05: `Init` with `controls.freeze_authority = controls.admin`, against a vault whose slot 2 holds
that configuration's id, is accepted and writes a configuration whose live freeze authority contains the
admin. SPEC-v2 §7 says of the admin and the freeze authority "the two must differ", and the bridge wire's
`FreezeAuthority::check` refuses the admin as a member, but only at a role handover (`ProposeRoles`); the
vault refuses it at construction (`vault/src/FerrataVault.sol` 600, `RolesMustDiffer`). In such a configuration the admin can freeze and run `Sunset`, which
`docs/trust.md` §4 says the admin cannot. Bounded: `configId` commits to the controls, so the roles are
visible before anyone deposits. Fix: the same check at `Init`; it changes the bridge program's image id,
so it belongs with the other bridge changes of milestone B1. Not fixed here.

**O1 (privacy observation, documented residual): a private claim's public part names its fee-schedule
range.** BR-PRV-01 searched the private claim's whole transaction (8,993 bytes) for the deposit's
link: none of `s`, `C`, the leaf, the depositor, the path or `fid` appears, but the 8-byte leaf index
did, twice: it is the `from_leaf` of the `ScheduleRange` the `Issue` boundary message carries
(`{index 1, from_leaf 6, until_leaf 8}`), which equals the leaf index because the deposit is schedule
1's first leaf. The range is public by design (`lez/bridge-wire/src/lib.rs`, `ScheduleRange`: "A private
claim so publishes the range, not the leaf index") and `docs/trust.md` §8 lists the fee-schedule change
as a residual correlation; what the run adds is that the range narrows a claim to the leaves the newest
schedule's known range covers (here 2 leaves), not only to a date. Specification ambiguity against
RFP-022 Privacy #1; not a program bug.

**O2 (error codes): an adoption part sent out of order is refused as `Malformed` (1), not
`StepError::Phase` (81).** LC-COM-10 and LC-COM-11 (a part replayed, part 1 first) are refused, as the
specification requires, with the core's code: `crates/ferrata-core/src/witness.rs` 887–894
(`AdoptionProgress::add_part` returns `Malformed` for an index other than the next part), while
`StepError::Phase` is documented for "a step that does not follow the job's last one (skipped or
replayed)". Specification ambiguity (RFP-021 U.5 asks for actionable codes); no safety effect.

## Not run, and why

- **Harness errors (2)**: BR-TEN-01 and BR-TEN-02: the test's setup of a third configuration B' failed
  (its `Register` refused 101 on the test's own synthetic block), so neither vector reached its
  decisive transaction. The test, not the program, is wrong; to be fixed before these two count.
- **Not expressible with the fixtures (1)**: LC-GL-04: the first Gloas update of the Sepolia fixture has
  no zero padding node to tamper with in its normalized branches.
- **Not implemented in this run (9)**: BC-01 to BC-06 (the bridge core's commitments and nullifiers),
  LC-SIG-15, LC-PART-04, LC-PART-05 (native-core participation and identity-key cases): stopped for the
  session's budget; the vectors stand as written for a later run.

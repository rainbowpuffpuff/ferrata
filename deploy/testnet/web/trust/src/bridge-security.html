What you trust

Nothing in Ferrata takes a party's word for a fact: an attestation is accepted because the LEZ program verifies Ethereum's sync-committee signatures from a pinned checkpoint and the Merkle proofs under it; a claim, because the bridge program proves the deposit under a root the attestation program attested; a release, because the vault verifies a zero-knowledge proof of the burn. Every off-chain party (updaters, provers, relayers, RPC providers) only carries data those checks accept or refuse: its role is liveness only. Four assumptions remain:

Caps, delays and freezes on this vault

As read back from the vault in the deployment record (it was deployed capped: "uncapped": false):

  • Caps: per day, deposits and releases each at most 10 ETH for ETH and 1,000,000 TUSD for the test token (6 decimals); a global daily cap on each (1,030,000,000,000 value units); an immutable release floor of 300,000,000 value units a day, so that no admin can throttle releases below it. Each bucket refills over a day.
  • Δ (outbound finality wait): 3,600 s, equal to its floor; the admin may only raise it.
  • Timers: revocation window 86,400 s (1 day); minimum release delay 0; release delays are set by the admin between the two. The design's production values are 7 days and 24 hours (vault/script/DeployVault.s.sol); this network uses short ones so a round trip fits a demonstration.
  • Freezes lapse after maxFreeze: 2,592,000 s (30 days), immutable. With no checkpoint progress for 30 days plus one candidate wait, anyone can retire the vault, no key needed; refunds then open after a sunset checkpoint and its revocation window (docs/trust.md §4.3).

RISC Zero's Groth16 advisory, and our correction

On 11 November 2026 RISC Zero published GHSA-g6qg-9j8p-7j87 and GHSA-mm6c-35cm-g4x2: Groth16 verifiers up to 3.0.x accept a receipt whose claim was swapped for an attacker's. Our security note of 21 November records that we acted only on 21 November, after a code review raised it, and what we did: caps set on the four older Sepolia vaults, which will not be used again; the move to RISC Zero 3.1.

Corrected 23 November 2026. The note first said the light client's public path did not depend on RISC Zero. It does: on LEZ v0.4 a privacy-preserving transaction's calls to public programs are applied on the strength of its proof alone, and LEZ v0.4.0-rc1 and rc3 accept a Groth16 receipt under the affected versions. So if LEZ accepts a forged receipt (not tested: no forgery was built), it could write any of our programs' state: the attestation instance's records, the bridge program's mints. The fix is LEZ's: a LEZ release on RISC Zero 3.1.

What that means here. The note and docs/trust.md said "no v0.4 program of ours runs on a public network". That was true when written and stopped being true on 23 November 2026, when this public test network started running them on LEZ v0.4.0-rc3 with RISC Zero 3.0.5; both documents now carry a dated correction. The new vault verifies with 3.1.0, but a release still rests on burns the LEZ side recorded, and the LEZ side rests on LEZ's check. Test value only; the vault's caps bound what a forgery could take.

Verify this site

Every file this host serves from the repository is listed, with its SHA-256 and the commit it comes from, in manifest.json. The same manifest is committed in the repository. A check that matters compares three things from outside this host. Most of the commits it names are not public yet (the test network's branches have not been merged); until they are, a file at such a commit can be checked against the manifest, not against its source. The manifest marks each file's commit public or not.

A check run by this page proves nothing if this host is compromised: a host that alters the wallet can alter this page and its script too, and make them say "all equal". The button below is a convenience for spotting a broken deploy. The check that holds against the host is the script, run on your machine from a clone of the repository.

The check that holds: run it yourself

git clone https://github.com/rainbowpuffpuff/ferrata && cd ferrata
python3 -I scripts/site-manifest.py verify -v --second https://THE-NAME-IN-YOUR-ADDRESS-BAR
python3 -I scripts/site-manifest.py verify --github main      # the manifest committed on GitHub, read from GitHub

It compares:

  1. The manifest this host serves (/bridge/verify/manifest.json) with the manifest committed in the repository (your clone's copy, or GitHub's with --github REF). They must be byte-identical; the repository's copy is the reference.
  2. Every listed file as this host serves it, hashed on your machine, with the manifest, and, where your clone has the listed commit, with the file read from git.
  3. The same files fetched again under the host's other name (--second: give the name you browse with; the default site is the network address in scripts/reproduce/deployed-programs.json; another TLS name and Host header) with a browser's User-Agent, so a host serving the checker one thing and browsers another has to tell them apart by IP address alone.

It also checks the security headers (Content-Security-Policy with script-src 'self' on every page, HSTS, nosniff, frame-ancestors 'none'). Exit status 1 on any difference.

What no check of a website can do

  • Targeted serving. A host can serve altered files only to some visitors (by IP, time or cookie) and the right ones to anyone who checks. The check shows what you were served when you ran it. For the wallet, which holds keys, the safest route is to run it from your clone: its files are plain static files (deploy/testnet/web/wallet/).
  • Files the manifest does not list. HTTP gives no directory listing; the manifest lists what was on the host when it was made, and the files it could not match to the repository are named below.
  • Server-side behaviour. The RPC gateway and faucet are programs; their source is public (deploy/testnet/host/) but what runs cannot be proven from outside. What the chain says can: read it from your own LEZ node.

The manifest

Made from the host's own file list after each deploy: each served file matched by its SHA-256 and path to a committed file under deploy/testnet/ or names/js/ (scripts/site-manifest.py build). Files the host writes itself (status, configuration with deployed accounts) are listed without a hash; files that match no committed file are named. This page cannot hold the manifest's numbers: its own SHA-256 is in the manifest.

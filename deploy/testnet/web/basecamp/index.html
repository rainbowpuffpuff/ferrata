Verify before you install

Three ways to tie a package to the release key. Each counts only when its output says what is shown under it: the key it names must be the one above (and the repository's copy), since a key file fetched from the same host as the packages proves nothing by itself. modules/scripts/basecamp-release.sh verify DIR runs all three on a downloaded release and stops at the first failure.

1. The signed list, then the files (ssh-keygen, sha256)

# download each package into a folder named as in SHA256SUMS (linux-amd64/ or darwin-arm64/), then:
curl -fsSLO https://<this host>/basecamp/dl/SHA256SUMS -O https://<this host>/basecamp/dl/SHA256SUMS.sig
curl -fsSLO https://<this host>/basecamp/dl/keys/allowed_signers
ssh-keygen -Y verify -f allowed_signers -I ferrata-release -n file -s SHA256SUMS.sig < SHA256SUMS
# must print: Good "file" signature for ferrata-release with ED25519 key SHA256:m5xC7zkg0LzI3YhCtol4qSfgMJGijs84mFWWGk0eX9Y
shasum -a 256 -c --ignore-missing SHA256SUMS     # Linux: sha256sum -c --ignore-missing SHA256SUMS
# must print "<file>: OK" for every package you downloaded (with none in place it checks nothing)

Or one file at a time, with its own .sig (the same "Good … SHA256:m5xC7zkg0LzI3YhCtol4qSfgMJGijs84mFWWGk0eX9Y" line):

ssh-keygen -Y verify -f allowed_signers -I ferrata-release -n file -s ferrata_bridge_module-0.1.0.lgx.sig < ferrata_bridge_module-0.1.0.lgx

2. minisign

minisign -Vm ferrata_bridge_module-0.1.0.lgx -P RWR2G/nU2CGRhoHnGsEDTix4ujwTsPJQ0gEsZsnjDBw6tEdUdQruoGjO
# must print: Signature and comment signature verified

3. Logos's own check: the signature inside the package

Each package carries manifest.sig: an Ed25519 signature over its manifest, which holds the hash of every file. Logos Core and Basecamp check it at install and name the signer. With lgx (logos-package) and a keyring that holds the release key only:

lgx keyring add ferrata did:jwk:eyJjcnYiOiJFZDI1NTE5Iiwia3R5IjoiT0tQIiwieCI6ImdlY2F3UU5PTEhpNlBCT3c4bERTQVN4bXllTU1IRHEwUjFSMUN1NmdhTTQifQ --dir ./keyring
lgx verify ferrata_bridge_module-0.1.0.lgx --keyring-dir ./keyring
# must print both: "Signature is valid" and "Signer is trusted: ferrata"
# lgx verify exits 0 for an unsigned package and for an unknown signer too: read its words, not its exit code

Install

In Logos Basecamp (desktop)

  1. Basecamp 0.4.0-rc.2, a pre-release: tag pre-release-4cea4bb-1433 on github.com/logos-co/logos-basecamp/releases. For Linux x86-64, logos-basecamp-x86_64.AppImage (293,951,992 bytes, SHA-256 e59e14cddd211bed763c49e6a9bdfea462b91123b368386bdb8f700527b747a0): make it executable and run it (without FUSE: --appimage-extract-and-run). The stable 0.3.2 installs these packages too, but names no signer.
  2. Package Manager (the cube in the sidebar) → Install Local Package: ferrata_bridge_module-0.1.0.lgx first, then ferrata_bridge_ui-0.1.0.lgx.
  3. The first dialog names the signer: “Ferrata release (test network)” · key 761B F9D4 D821 9186. Compare the key with the one at the top of this page, then choose Trust & install: Basecamp adds the key to its keyring (Settings → Trusted Publishers), the mini-app then installs as “signed by Ferrata release (test network)”, and an update signed by another key will ask again.
  4. Settings → Module Inspector → Ferrata bridge → Load. The mini-app does not declare the module as its dependency yet, so Basecamp does not start it; without it the mini-app waits for its backend.
  5. Open Ferrata Bridge from the sidebar.

Run by us on 24 November 2026 with the 0.4.0-rc.2 and 0.3.2 AppImages on Linux x86-64: both installed both packages from these files and opened the mini-app. 0.4.0-rc.2 showed the dialog above, and refuses to start an installed app whose files changed after the install; 0.3.2 names no signer (its dialog only says the request came from its unsigned Package Manager) and installs on Install.

What the mini-app can do there today: its eight screens open and explain each step and what it makes public. It cannot reach this network or Sepolia yet: every call answers “no wallet session”. The bridge module's session is opened with a chain service (in this repository a stand-in for Logos's Ethereum and LEZ modules, which we run beside our own LEZ sequencer), the mini-app has no control that opens one, and the module in these packages reads only http:// endpoints. So in Basecamp it does not yet read the registry or the vault, plan a deposit or recover positions from a seed, and Endpoints' “Apply and test” answers “Not switched”. We ran the whole round trip inside Basecamp on our own LEZ sequencer with that stand-in (below).

In a headless Logos Core (logosctl)

printf 'signature_policy: require\n' > node.yaml     # refuse unsigned packages and unknown signers
logosctl daemon config set node.yaml
DID=did:jwk:eyJjcnYiOiJFZDI1NTE5Iiwia3R5IjoiT0tQIiwieCI6ImdlY2F3UU5PTEhpNlBCT3c4bERTQVN4bXllTU1IRHEwUjFSMUN1NmdhTTQifQ

The withdrawal, to the end

Getting tokens back to Ethereum is the hard half of a bridge: the user burns on LEZ, the zone's burns are checkpointed to the vault with a proof, and the vault pays out only against a proof of that burn. All of it is in these packages.

  1. 1. BurnPrivate by default, to a fresh Ethereum address. mini-app → bridge module (burn), proven by LEZ's wallet
  2. 2. CheckpointThe zone's burn root goes to the vault with a RISC Zero proof. relayer
  3. 3. Release proofThe burn's release witness and journal; the proof wrapped for Ethereum (Groth16). bridge module (release), relayer
  4. 4. ReleaseThe vault verifies and pays the fresh address; the relayer pays the gas. relayer → vault

Reproduce

The packages are built from a clean checkout of public main by one script, the way the repository's macOS workflow builds them: each module exported as its own repository, nix build .#lgx-portable, lgx verify. Every input is pinned, so the same commit should give the same bytes; compare yours with the unsigned SHA-256 in release.json (signing adds the signature file, so the signed package's SHA-256 differs; its rootHash does not). Needs Nix with flakes, git, curl, jq and python3; on Linux the updater also needs LEZ's guests built first, with Rust and RISC Zero 3.0.5 and a RISC Zero home holding guest Rust 1.91.1 (RISC0_HOME, as lez/RESULTS.md says). On a Mac the updater is left out and RISC0_HOME is not needed.

git clone https://github.com/rainbowpuffpuff/ferrata && cd ferrata && git checkout a0f388279e2de21305e0a8d1b0777f627ad165b9
scripts/fetch-upstream.sh
RISC0_HOME=<RISC Zero home with guest Rust 1.91.1> modules/scripts/basecamp-release.sh build . ../out
jq -r '.packages[] | "\(.sha256)  \(.file)"' ../out/build.json     # compare with release.json's unsigned_sha256

7 of 7 byte-identical The Linux packages were built twice from commit a0f38827 in two Modal containers of two workspaces, each with its own Nix store (a Modal build box in one workspace, its Nix store restored from an earlier stream's; a Modal build box in another workspace, a fresh container and an empty Nix store; both fetch from cache.nixos.org and the same pinned sources): every package came out with the same SHA-256 (tests/reproduce.json).

What is live, and what is not

Live

  • This LEZ v0.4.0-rc3 network: blocks, the faucet, the explorer, the web wallet.
  • The Sepolia light client on the zone, kept up by the updater (the attestation module reads it).
  • These 13 packages, signed, with their SHA-256 and the key in four forms.
  • The RISC Zero 3.1 vault on Sepolia, named in this network's bridge configuration (see the withdrawal table).

Not yet

  • A withdrawal on this network recorded in this repository: the bridge is paired; /status/ says where the network stands.
  • The mini-app on this network inside Basecamp: it installs and opens (0.4.0-rc.2, 24 November 2026), but cannot open its session here or on Sepolia, so in Basecamp it reads and sends nothing yet (Install).
  • The mini-app for macOS built by the macOS workflow: the one here is assembled from the Linux build's files (it has no native code), and nobody has opened it in Basecamp on a Mac yet.
  • A second macOS build to compare bytes with (the Linux packages were built twice, byte-identical).
  • A published Logos catalog: these packages are installed from files, not from a catalog.
  • An audit: everything here is a prototype.
